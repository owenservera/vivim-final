## WHAT V6 IS

"The Living Canvas" — a spatial node-based workspace where each UI element
is a "node" that streams real-time data from the vivim-final backend.

### 10 Killer Solutions (from brief)

1. **Streaming-Native Nodes** — every node opens an SSE/WS channel to
   `/api/capabilities/:id/execute` (file 1 §Capability Router). The node's
   `onCapabilityRequest` callback sends the execute request; the response
   streams in as ContentPart[] chunks (file 1 §Streaming Response Helper).

2. **Agent Co-Pilot (Canvas Intelligence)** — an AI assistant embedded in the
   canvas that can: create/delete nodes, connect them, adjust layouts.
   Uses `POST /api/interpret` (file 1 §Interpret Router) with
   `{ nlText: "create a chat node for provider X", routeHints: { surfaces: ['ui'] } }`.
   The returned `capabilitiesToExecute` array drives node creation.

3. **Semantic Zoom** — zoom levels don't just scale; they change what's
   visible:
   - zoom > 2: show full node internals (sandbox iframe content)
   - zoom 0.5-2: show node shells with titles and status
   - zoom < 0.5: show collapsed node summaries with connection lines
   Implement in CanvasSurface's `visibleSlots` filter using viewport.zoom.

4. **Universal Node Type System** — use vivim-final's actual
   `UnifiedCapability` interface (file 1 §Engine Types) as the node type
   contract. Each node displays: capability slug, provider, tier, status,
   streaming state. The `Primitive` type (file 3 v5 conceptual-model)
   maps directly to capability surfaces.

5. **Real-time Collaboration (CRDT)** — multiple users see the same canvas
   state. Use the WebSocket protocol (file 1 §WebSocket):
   - On connect: send `{ type: 'hello', sessionId, role: 'frontend' }`
   - Subscribe to canvas events: `{ type: 'subscribe', entityType: 'canvas', entityId }`
   - Broadcast layout changes via `{ type: 'canvas:node:moved', nodeId, layout }`
   Use Yjs or Automerge for CRDT state sync.

6. **Intent-Based Auto Layout** — nodes auto-arrange based on:
   - Capability category (from `category` field on UnifiedCapability)
   - Provider grouping (nodes from same provider cluster together)
   - User intent hints from the command palette
   Implement as a layout engine that computes node positions from
   capability metadata, then animates to positions.

7. **Local-First / Offline** — canvas layout + node definitions cached
   in IndexedDB. On reconnect, sync changes to backend via:
   - `POST /api/capabilities/:id/execute` for capability changes
   - WebSocket for layout state sync
   Use a sync queue pattern: pending changes stored locally, flushed on reconnect.

8. **Command Palette as OS** — the command palette (from V5's Phase 3)
   is the primary interaction surface:
   - Type `/` to open palette
   - Search capabilities from backend: `GET /api/capabilities?surface=ui`
   - Execute directly: `POST /api/capabilities/:id/execute`
   - Create nodes from palette results
   - Navigate: switch conversations, providers, workspaces

9. **Accessibility (WCAG 2.1 AA)** — every node is focusable, has aria
   labels, keyboard navigation (arrow keys move focus between nodes),
   screen reader announcements for streaming updates.
   Use `role="application"` on canvas, `role="article"` on nodes.

10. **Observability Panel** — a collapsible side panel showing:
    - Active WebSocket connections and their status
    - Capability execution history (from WS events)
    - Provider health (from `GET /api/providers/:id/health`)
    - Engine metrics (from WS `engine:*` events)
    This panel subscribes to the WS event stream and renders a live log.

## vCARD SYSTEM (WIDGET CAPABILITY MENU)

Every node on the canvas is a "vCard" — a self-contained widget with a
hierarchical capability menu. The menu has two layers:

### Global Actions (available on ALL vCards)

These appear in every node's context menu (right-click or `⋯` button):

| Action | Icon | Description |
|---|---|---|
| Collapse | `▾` | Minimize to title bar only (height → 32px) |
| Expand | `▴` | Restore from collapsed state |
| Pin | `📌` | Fix node position — disables drag. Toggle. |
| Full Screen | `⛶` | Maximize node to fill entire canvas viewport |
| Duplicate | `⧉` | Clone node with same config, offset position |
| Detach | `↗` | Pop out into a separate browser window |
| Settings | `⚙` | Open node-specific settings drawer (right panel) |
| Connections | `⤴` | Toggle I/O line visibility for this node |
| Thread | `💬` | Open dedicated conversation thread for this node |
| Remux | `🔀` | Re-route this node's output to a different target |
| Inspect | `🔍` | Show raw capability response, WS events, timing |
| Remove | `✕` | Disconnect and remove node from canvas |
| Export | `↓` | Export node config as JSON / share link |
| History | `↻` | Show undo/redo stack for this node |
| Lock | `🔒` | Prevent all changes (layout, config, connections) |

### Per-Widget-Type Actions

Each capability category adds its own actions to the global set:

**Chat nodes** (`category: chat`):
- `New Thread` — start fresh conversation in this node
- `Branch` — fork current conversation into a new thread
- `Merge` — merge two conversation threads
- `Clear Context` — reset conversation history
- `Export Transcript` — download as markdown/JSON
- `Model Select` — switch provider model mid-conversation
- `System Prompt` — edit the system prompt for this thread
- `Temperature` — adjust creativity slider

**Tool nodes** (`category: tool`):
- `Configure` — open tool settings drawer
- `Test Run` — execute with sample input
- `View Schema` — show input/output JSON schema
- `Enable/Disable` — toggle tool availability
- `Permissions` — manage access scope

**Memory nodes** (`category: memory`):
- `Recall` — search memory entries
- `Forget` — delete specific memory entries
- `Consolidate` — merge duplicate memories
- `Export` — download memory store
- `Import` — upload memory entries

**File nodes** (`category: file`):
- `Open` — open file in viewer/editor
- `Download` — save to local disk
- `Upload` — replace file content
- `Version History` — show file versions
- `Diff` — compare with another version

**Provider nodes** (`category: provider`):
- `Health` — show provider health dashboard
- `Rate Limits` — show current rate limit status
- `Switch Model` — change model within provider
- `Test Connection` — verify API key works
- `Usage` — show token/cost usage

## VISUAL CONNECTION I/O LINES

Nodes can be connected via configurable I/O lines. Lines represent
data flow between capabilities.

### Line Types

| Line Type | Visual | Use Case |
|---|---|---|
| Data Flow | `───→` solid arrow | Output of A feeds input of B |
| Reference | `╌╌╌→` dashed arrow | A references B's data (no copy) |
| Stream | `≋≋≋→` wavy arrow | Real-time streaming data |
| Control | `···→` dotted arrow | A triggers B (no data transfer) |
| Feedback | `←───` reverse arrow | B's result feeds back into A |

### Line Configuration

Each line has configurable properties:

```typescript
interface ConnectionLine {
  id: string
  from: { nodeId: string; port: 'output' | 'stream' | 'error' }
  to: { nodeId: string; port: 'input' | 'config' | 'context' }
  type: 'data' | 'reference' | 'stream' | 'control' | 'feedback'
  label?: string           // optional label on the line
  color?: string           // customizable color
  animated?: boolean       // animate flow direction
  throttleMs?: number      // rate limit data flow
  transform?: string       // optional data transform expression
  conditional?: string     // only connect if condition is true
}
```

### Line Rendering

- Lines follow bezier curves between node ports
- Port positions are calculated from node layout (right = output, left = input)
- Animated lines show flow direction (CSS animation on stroke-dashoffset)
- Hovering a line shows its label and data type
- Clicking a line opens a config popover (change type, add transform, etc.)
- Lines are viewport-culled (same as nodes) for performance

### Port System

Each vCard has standardized ports:

| Port | Side | Type | Description |
|---|---|---|---|
| `input` | Left | data | Primary data input |
| `config` | Left | config | Configuration/settings input |
| `context` | Left | context | Context bundle input |
| `output` | Right | data | Primary data output |
| `stream` | Right | stream | Real-time streaming output |
| `error` | Bottom | error | Error/exception output |

## THREADS, REMUX & AGENTIC WORKLOADS

### Dedicated Threads

Every vCard can own a dedicated conversation thread. This thread is:
- Persisted in the backend (`POST /api/conversations`)
- Subscribed via WebSocket for real-time updates
- Visually distinct: shown as a mini-chat inside the node
- Independent: has its own message history, system prompt, model config

Thread states are shown with visual indicators:

| State | Visual | Meaning |
|---|---|---|
| Idle | `○` gray dot | Thread exists, no active stream |
| Streaming | `◉` pulsing blue | Actively receiving tokens |
| Thinking | `◎` spinning ring | Agent is processing (tool calls, etc.) |
| Error | `●` red dot | Last response had an error |
| Paused | `◌` half-dot | User paused the stream |
| Complete | `✓` green dot | Response finished successfully |

### Remux (Re-routing)

Remux redirects a node's output to a different target without changing
the node's internal state. Use cases:
- Send chat output to a different provider
- Route tool results to a file instead of chat
- Redirect streaming data to a visualization node

Remux is configured via the thread panel's "Remux" button or via
the `/remap [from] [to]` slash command.

### Agentic Workloads

Agentic workloads are multi-step operations that the backend orchestrates.
They appear on the canvas as special "agentic" nodes:

```typescript
interface AgenticWorkload {
  id: string
  name: string
  steps: Array<{
    nodeId: string
    capabilityId: string
    input: Record<string, unknown>
    status: 'pending' | 'running' | 'complete' | 'error'
    output?: unknown
  }>
  status: 'planning' | 'executing' | 'complete' | 'error'
  progress: number  // 0-100
  createdAt: number
}
```

Visual design for agentic nodes:
- Distinct border: gradient from blue (planning) → green (executing) → gold (complete)
- Step indicator: horizontal progress bar with step markers
- Each step shows: icon, name, status dot, duration
- Collapsible: can minimize to just the progress bar
- Logs: expandable panel showing each step's input/output

## DATA LAYER: STORAGE, FILES, CONVERSATIONS

The frontend maintains a local data layer that syncs with the backend
and external sources.

### Conversation Sync

The frontend can sync conversations from external providers:
- ChatGPT conversations (via the backend's ChatGPT provider)
- Gemini conversations (via the backend's Gemini provider)
- Claude conversations (via the backend's Claude provider)

Each synced conversation becomes a "data card" on the canvas:
- Shows: provider icon, conversation title, message count, last activity
- Click to open in a dedicated thread
- Drag to add as context bundle
- Searchable via the command palette

Sync is triggered by:
- `GET /api/conversations?provider=chatgpt` — list synced conversations
- `GET /api/conversations/:id/messages` — fetch full message history
- WebSocket events: `conversation:synced`, `conversation:updated`

### File Store

Local file storage for:
- Uploaded files (drag-and-drop onto canvas)
- Exported conversations (markdown, JSON)
- Canvas snapshots (for backup/restore)
- Context bundles (saved combinations of files + conversations + memories)

File store uses IndexedDB with the following schema:

```typescript
interface FileEntry {
  id: string
  name: string
  mimeType: string
  size: number
  data: Blob
  tags: string[]
  source: 'upload' | 'export' | 'sync' | 'snapshot'
  createdAt: number
  updatedAt: number
}
```

### Memory Layer

The frontend maintains a local memory cache that syncs with the backend's
memory engine (`POST /api/capabilities/cap:memory:memory/execute`).

Memory entries appear as small "memory nodes" on the canvas:
- Draggable into context bundles
- Searchable via command palette
- Visual: brain icon with confidence indicator
- Types: episodic (conversations), semantic (facts), procedural (how-to)

### Dynamic Context Bundles

Context bundles are saved combinations of:
- Files (from file store)
- Conversations (synced or local)
- Memory entries
- Tool configurations
- Provider-specific context

Bundles are stored locally and can be:
- Shared via URL (serialized to query params)
- Exported as JSON
- Imported from JSON
- Applied to any vCard via drag-and-drop

Bundle application shows a visual "loading" state on the target node:
- Brief animation: bundle items fly from the bundle panel to the node
- Node updates its context display
- Backend is notified via `POST /api/capabilities/:id/execute` with
  the bundle data as part of the input

## INTEGRATION POINTS

All requests go through these backend endpoints (from file 1):

### Read Operations
- List capabilities: `GET /api/capabilities?surface=ui&category=chat`
- List conversations: `GET /api/conversations`
- List providers: `GET /api/providers`
- Get workspace config: `GET /api/config`
- Get provider health: `GET /api/providers/:id/health`

### Write Operations
- Execute capability: `POST /api/capabilities/:id/execute`
- Create conversation: `POST /api/conversations`
- Send message: `POST /api/conversations/:id/messages`
- NLCL interpret: `POST /api/interpret`
- Update config: `PUT /api/config`

### Real-time
- WebSocket: `ws://localhost:9420/ws`
  - Subscribe: `{ type: 'subscribe', entityType: 'conversation', entityId }`
  - Events: `conversation:*`, `capability:*`, `provider:*`, `engine:*`
  - Streaming: capability execution responses arrive as chunked events
