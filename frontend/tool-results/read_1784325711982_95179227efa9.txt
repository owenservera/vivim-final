     7→# DOC 11 — COMBINATORIAL DESIGN: ONE UI, MANY APPS, ANY REMIX
     8→
     9→> Companion to DOC 1–10. This document (1) formalizes the conceptual vision the user described — UI components as *representations of provider capabilities*, (2) defines the **component→provider registry tree** + the **workspace remix model**, and (3) generates **100 combinatorial scenarios** that the resolution engine + routers must handle for *any* provider type × *any* component type × *any* account tier, shared and not-shared, across workspaces.
    10→
    11→---
    12→
    13→## PART A — THE CONCEPTUAL VISION (what we are really building)
    14→
    15→### A.1 UI components = capability representations
    16→
    17→Every visible thing on the canvas is not "a widget." It is a **rendering of a capability** that a provider exposes.
    18→
    19→- The **send button** is the rendering of `cap:message:send`.
    20→- The **message box / composer** is the rendering of `cap:message:compose`.
    21→- The **thread** is the rendering of `cap:conversation:list`.
    22→- The **streaming result** is the rendering of `cap:response:stream`.
    23→
    24→These capabilities are **shared across providers**. `cap:message:send` exists for ChatGPT, Gmail, WhatsApp, and Twitter. That is why we can have **one UI, many apps**: a single `chat.send` component can render the send action for 50 different providers, because the *capability* is the same even when the *provider* differs.
    25→
    26→### A.2 The component → provider registry tree
    27→
    28→Resolution is a **tree walk** from the most specific binding to the most generic:
    29→
    30→```
    31→LEVEL 0  system built-in default          (hardcoded fallback, last resort)
    32→   │
    33→LEVEL 1  cross-type  (ownerId='global')   ← SHARED across ALL providers/families
    34→   │
    35→LEVEL 2  family      (ownerId=familyId)    ← SHARED across one family (ai-chat, email, ...)
    36→   │
    37→LEVEL 3  family+variant (ownerId=familyId, variant)
    38→   │
    39→LEVEL 4  provider    (ownerId=providerId)  ← provider-specific override
    40→   │
    41→LEVEL 5  provider+variant (ownerId=providerId, variant)  ← most specific
    42→```
    43→
    44→Each level is a `UiComponent` row keyed by `(primitiveId, scope, ownerId, variant)`. The resolver walks **5 → 4 → 3 → 2 → 1 → 0** and returns the first hit. This is the 4-tier model extended to 6 explicit levels (the POC's hardcoded tool set is replaced by this data-driven tree).
    45→
    46→**Key insight:** the tree is *sparse*. Most providers have NO provider-level override, so they inherit the cross-type or family component. That is the "one UI, many apps" effect — 90% of providers render from shared rows; only the different ones get an override leaf.
    47→
    48→### A.3 Account tier gates the capability (not just the component)
    49→
    50→A component can resolve, but the *capability it represents* may be **tier-gated**:
    51→
    52→- `ProviderAccount.planTier` ∈ {anonymous, free, trial, pro, enterprise}
    53→- `CapabilityTaxonomy.minPlanTier` — minimum tier to even see the capability
    54→- `CapabilityTier` — per-tier UI overrides (e.g., `pro` gets an "export all" button the `free` tier doesn't)
    55→
    56→So resolution is **two-phase**:
    57→1. **Component resolution** (the tree walk above) → *which UiComponent renders*.
    58→2. **Capability gating** (tier check) → *whether it's enabled / what sub-actions show*.
    59→
    60→A `free` account on ChatGPT resolves the same `chat.send` component as `enterprise`, but `enterprise` additionally sees the `cap:export:all` action because its `CapabilityTier` unlocks it.
    61→
    62→### A.4 The workspace = the remix container
    63→
    64→A **workspace** binds a named set of `(provider, account)` pairs and chooses a **global UI component set**. The same global component (`chat.composer`) can be used in:
    65→
    66→- **Workspace A**: {ChatGPT(free), Gmail(free)} → composer renders with free-tier actions only.
    67→- **Workspace B**: {ChatGPT(pro), Slack(enterprise)} → same `chat.composer` component, but now pro/enterprise actions appear because the accounts behind it are higher tier.
    68→
    69→The component is **shared**; the *resolution context* (which providers/accounts are in the workspace) changes what it renders and what it enables. This is the user's core ask: **combine XYZ providers (same type and/or different types) under one global UI, with different combinations of providers and accounts per workspace.**
    70→
    71→### A.5 What the engine + router must GENERATE
    72→
    73→Given the above, the generated system must, for *any* triple (providerType × componentType × accountTier), produce:
    74→- a resolved `UiComponent` (or explicit `fromSystemDefault` fallback),
    75→- a tier-gated action set,
    76→- a per-workspace layout,
    77→- and the routers (`cap:canvas:*`, `cap:conceptual:*`, `cap:conversation:*`) that serve it.
    78→
    79→The 100 scenarios below are the **acceptance matrix** for that generator.

   253→# DOC 12 — SYNCHRONOUS ROUTING + LOGGING COUPLING/DECOUPLING ALGORITHM
   254→
   255→> Companion to DOC 11 (100 scenarios). This defines the **routing algorithm** (how a request for any provider×component×tier×workspace resolves synchronously and fans out), the **logging/coupling model** (what is tightly coupled by `traceId` and what is decoupled by the event bus), and proves both against the 100 scenarios as a validation matrix. Grounded in the real `CapabilityEventBus`, `TraceEntry`, and `StructuredLogger` already in `src/`.
   256→

   258→
   259→## PART A — PRIMITIVES (from the real codebase)
   260→
   261→| Primitive | Source | Role in algorithm |
   262→|---|---|---|
   263→| `CapabilityEventBus` | `src/engines/capability-event-bus.ts` | In-process pub/sub + WS forwarder. The **decoupling** backbone. |
   264→| `traceId` (ULID) | `src/ids.ts`, `src/engines/capability.ts` | Correlation key. The **coupling** backbone (synchronous request↔response↔log). |
   265→| `TraceEntry` | `prisma/schema.prisma:422` | Structured, queryable log row (engine, method, providerId, accountId, conversationId, durationMs, ok, error). |
   266→| `StructuredLogger` | `src/engines/logger.ts` | Emits `TraceEntry`-shaped spans. |
   267→| `CanvasLayerMounter` | `src/engines/canvas-layer-mounter.ts` | Emits `canvas:layer:spawned/dismissed` — the live coupling point to the frontend. |
   268→| Governor Canon | AGENTS.md | Engines **emit only**; they never touch DOM/CDP. Decoupling guarantee. |
   269→
   270→**Core law:** *Synchronous path is coupled by `traceId`; asynchronous fan-out is decoupled by the event bus.* A request must return a resolved answer on the calling thread (synchronous routing), while side-effects (spawn UI, stream, log, notify WS) are emitted as events and resolved independently.

   273→
   274→## PART B — THE SYNCHRONOUS ROUTING ALGORITHM
   275→
   276→### B.1 Request envelope
   277→
   278→Every canvas/conceptual request carries a **Resolution Context**:
   279→
   280→```ts
   281→interface RouteContext {
   282→  traceId: string                 // ULID, generated at entry
   283→  workspaceId: string
   284→  providerIds: string[]           // 1..N (multi-provider WS, S41–S50)
   285→  accountIds: string[]            // 1..N (multi-account, S09/S50/S86)
   286→  slotIds: string[]               // 1..13 (which components, S99)
   287→  userId: string
   288→}
   289→```
   290→
   291→### B.2 Algorithm: `routeSync(ctx)` — returns resolved surface in ONE pass
   292→
   293→```
   294→routeSync(ctx: RouteContext): ResolvedSurface
   295→  ╭─ COUPLED PHASE (synchronous, single traceId) ─╮
   296→  1. span = logger.start(ctx.traceId, 'route:sync', { workspaceId, providers: ctx.providerIds })
   297→  2. familyMap = ConceptualModelService.resolveFamilies(ctx.providerIds)   // FK walk (S95)
   298→  3. slots = []
   299→  4. for each providerId in ctx.providerIds:
   300→  5.    for each slotId in ctx.slotIds:
   301→  6.       accountTier = AccountStore.tierFor(ctx.accountIds, providerId)  // S09/S50/S86
   302→  7.       comp = UiComponentStore.resolve({
   303→  8.         primitiveId: slotToPrimitive(slotId),   // chat.send → prim:ai-chat:send (DOC 5.5)
   304→  9.         scopeChain: ['provider+variant','provider','family+variant','family','cross-type','system'],
   305→ 10.         ownerId: providerId, familyId: familyMap[providerId], variant: ctx.variant,
   306→ 11.         statusFilter: skip 'draft'|'deprecated'   // S66/S67/S68
   307→ 12.       })                                          // 6-LEVEL TREE WALK (DOC 11 Part A.2)
   308→ 13.       actions = CapabilityGating.resolveActions(comp.capabilityId, accountTier) // S51–S60
   309→ 14.       slots.push({ providerId, slotId, component: comp, tier: comp.tier,
   310→ 15.                     fromSystemDefault: comp.tier==='system', accountTier, actions })
   311→ 16.  surface = assembleWorkspace(ctx.workspaceId, slots)   // S71–S80 reuse logic
   312→ 17. logger.end(span, { slotCount: slots.length, ok: true })
   313→ 18. return surface
   314→  ╰─────────────────────────────────────────────────╯
   315→  ╭─ DECOUPLED PHASE (async emit, NOT awaited) ─╮
   316→ 19. eventBus.emit({ type:'canvas:surface:resolved', traceId: ctx.traceId,
   317→ 20.                  workspaceId, surface })        // fans out to WS subscribers
   318→ 21. return surface                                 // caller gets answer NOW (sync)
   319→```
   320→
   321→**Why synchronous:** The HTTP router (`cap:conceptual:surface`) and the React `useConceptualModel` hook need the full resolved surface *before* rendering — they block on `routeSync`. The 100 scenarios all require a deterministic answer *in the response* (S01 returns the same componentKey for 4 providers; S40 returns the deepest tier; S61 returns system default). Awaiting the event bus would break this.
   322→
   323→**Why decoupled:** Spawning the actual DOM nodes, streaming, logging to `TraceEntry`, and notifying other browser tabs happen via `emit` and do **not** block the return.
   324→
   325→### B.3 The 6-level tree-walk (coupled, deterministic)
   326→
   327→```
   328→resolve(ctx): UiComponent | null
   329→  for level in [provider+variant, provider, family+variant, family, cross-type, system]:
   330→    row = store.find({ primitiveId, scope:level.scope, ownerId:level.owner,
   331→                       variant: ctx.variant ?? null })
   332→    if row && row.status === 'published':
   333→      return row                      // FIRST HIT WINS (S30, S40, S89)
   334→  return null → caller uses system fallback (S61–S70)
   335→```
   336→- Exact variant match only (S98 unicode). No normalization.
   337→- `null` component → system default, `fromSystemDefault=true` (S70, S94).
   338→
   339→### B.4 Tier-gating (coupled, second phase)
   340→
   341→```
   342→resolveActions(capabilityId, tier):
   343→  cap = CapabilityTaxonomy.find(capabilityId)
   344→  if tier < cap.minPlanTier: return []            // S10, S51, S52, S59 hidden
   345→  tierRow = CapabilityTier.find(capabilityId, tier)
   346→  return tierRow?.uiComponentOverride ?? cap.baseActions   // S53, S56, S57 overrides
   347→```

   351→## PART C — LOGGING: COUPLING & DECOUPLING MODEL
   352→
   353→### C.1 What is COUPLED (by `traceId`)
   354→
   355→The synchronous request→resolution→response→persist chain shares ONE `traceId`. This makes any scenario **auditable end-to-end**:
   356→
   357→```
   358→traceId=T
   359→  ├─ route:sync (logger.start, span A)
   360→  ├─ conceptual:resolveFamily (span B, parent=T)
   361→  ├─ uiComponent:resolve x N (span C.., parent=T)   ← one per (provider,slot)
   362→  ├─ capability:gate x N (span D.., parent=T)
   363→  ├─ route:sync (logger.end, span A)
   364→  └─ TraceEntry rows all carry traceId=T, providerId, accountId, conversationId
   365→```
   366→
   367→Coupling by `traceId` is **mandatory** for: S54 (live tier upgrade must re-resolve under same conversation), S79 (WS switch re-resolve same user), S97 (provider deleted mid-session — must correlate old+new resolution), S100 (empty DB boot — all system defaults under one trace).
   368→
   369→### C.2 What is DECOUPLED (by event bus)
   370→
   371→Side-effects do NOT share the request's synchronous lifetime. They are emitted and forgotten:
   372→
   373→| Event | Emitted by | Consumed by (decoupled) | Scenarios |
   374→|---|---|---|---|
   375→| `canvas:surface:resolved` | routeSync (B.2:19) | WS forwarder → other browser tabs | S79, S96 |
   376→| `canvas:layer:spawned` | CanvasLayerMounter | `useCanvasEvents` frontend | S41, S78, S91 |
   377→| `canvas:layer:dismissed` | CanvasLayerMounter | `useCanvasEvents` frontend | S97 |
   378→| `capability:actions:changed` | CapabilityGating on tier change | `useCanvasEvents` → re-render actionBar | S54, S96 |
   379→| `workspace:reresolved` | WorkspaceResolver on provider add | `useConceptualModel` → toNodes() | S71–S80 |
   380→| `sandbox:denied` | SandboxedLayer CSP check | error tracker | S92, S93 |
   381→
   382→Decoupling guarantee = **Governor Canon**: emitters never await consumers; consumers never block emitters. The frontend can be closed and the backend still returns `routeSync` correctly (S77 empty WS, S100).
   383→
   384→### C.3 The coupling/decoupling boundary rule
   385→
   386→```
   387→RULE: A handler may ONLY mutate state it owns. Cross-boundary effects = emit, never call.
   388→  ✓ ConceptualModelService resolves → emits canvas:surface:resolved (does NOT call frontend)
   389→  ✓ CapabilityGating changes tier → emits capability:actions:changed (does NOT patch DOM)
   390→  ✗ Engine importing SandboxedLayer / React Flow = VIOLATION (S92/S93 safety depends on this)
   391→```
   392→
   393→This is exactly why S92 (malicious scriptUrl) and S93 (inline script attempt) are safe: the engine that *resolves* the component is decoupled from the *renderer* that *enforces* the sandbox. The resolver emits; the renderer (frontend, sandboxed) enforces `allowInlineScript:false`.
   394→

   397→## PART D — THE DECOUPLING/RE-COUPLING ALGORITHM (live updates)
   398→
   399→When context changes (tier upgrade, provider added, workspace switched), we **re-couple** a new synchronous pass under a *new* `traceId` but emit a delta so the frontend **decouples** the heavy re-resolve:
   400→
   401→```
   402→onContextChange(change: TierChange|ProviderAdded|WorkspaceSwitch, ctx):
   403→  newTrace = ulid()
   404→  surface' = routeSync({ ...ctx, traceId: newTrace })   // COUPLED re-resolve (sync)
   405→  delta = diff(surface_prev, surface')                  // compute minimal diff
   406→  eventBus.emit({ type:'workspace:reresolved', traceId:newTrace,
   407→                  workspaceId, delta })                  // DECOUPLED fan-out
   408→  // frontend applies delta only (no full re-mount) → S54/S79/S96/S97 smooth
   409→```
   410→
   411→This satisfies: S54 (pro upgrade → export appears), S79 (WS-A→WS-B switch → action set updates), S96 (same provider different tier per WS), S97 (provider deleted → re-resolve to family).

   460→// src/server/conceptual-router.ts — cap:conceptual:surface
   461→async function handleSurface(req: SurfaceRequest): Promise<ResolvedSurface> {
   462→  const traceId = ulid()                                   // C.1 coupling key
   463→  const ctx: RouteContext = {
   464→    traceId, workspaceId: req.workspaceId,
   465→    providerIds: req.providerIds, accountIds: req.accountIds,
   466→    slotIds: req.slotIds ?? ALL_SLOTS, userId: req.userId,
   467→  }
   468→  const surface = routeSync(ctx)                           // B.2 SYNCHRONOUS return
   469→  // DECOUPLED fan-out (fire-and-forget):
   470→  eventBus.emit({ type: 'canvas:surface:resolved', traceId, ...surface })
   471→  return surface                                           // caller blocked only on B.2
   472→}
   473→
   474→// Real-time context change (tier/provider/WS):
   475→eventBus.on('account:tier:changed', (e) => onContextChange(e, currentCtx))  // D
   476→eventBus.on('provider:added',      (e) => onContextChange(e, currentCtx))  // D
   477→```
