     7→# The Vivim Canvas: One Screen, Everything, Live
     8→
     9→## What We're Building
    10→
    11→Imagine opening a single browser tab — and that tab is not a webpage. It's a **space**.
    12→
    13→Not a dashboard. Not an app. A living workspace where every piece of the interface is a thing you can grab, move, resize, replace, or let an agent create for you on the fly. Chat. Email. Code. Dashboards. They're all just **nodes on a surface**, floating in a boundless infinite canvas.
    14→
    15→Right now, most software gives you a fixed grid. You get a sidebar here, a header there, a chat window somewhere else, and if you want to change that layout, you file a feature request and wait six months. The interface is **frozen** at compile time. The developers decided what you see, and that's what you get.
    16→
    17→We're building the opposite.
    18→
    19→---
    20→
    21→## The Core Idea: The Interface Is Data, Not Code
    22→
    23→In Vivim, the UI is stored in a database. Not a config file. Not a JSON blob. Real database rows — one per UI component — with the actual HTML, CSS, and (sandboxed) JavaScript that makes up each piece of the screen.
    24→
    25→Every component lives in a table. Each row says: "Here's the markup. Here's the styling. Here's what it does. Here's who it belongs to." When you open the app, the system looks at what you need — which provider, which family of tools, which variant — and **resolves** the right components for the right slots on the canvas.
    26→
    27→Change a row in the database, and the interface changes. No rebuild. No deploy. No restart. The canvas is **hot-swappable** by design.
    28→
    29→This means:
    30→
    31→- A new version of the chat composer? Write the HTML/CSS, update the row, and it's live for every user.
    32→- A custom sidebar for a specific provider? Add a provider-scoped component, and it overrides the default.
    33→- A family-wide theme for all email interfaces? Store it as a component row scoped to the `email` family, and every email provider inherits it.
    34→- An agent builds a new UI panel while you watch? It writes a component row, and the node appears on your canvas in real time.
    35→
    36→The shell doesn't know or care what's inside each node. It just resolves and renders. That's the power of making the UI **data**.
    37→
    38→---
    39→
    40→## The Canvas: An Infinite, Programmable Space
    41→
    42→The single screen is an infinite canvas powered by React Flow. Every UI region — the chat header, the message thread, the composer, the sidebar, the action bar, the streaming results — is a **node** on this canvas.
    43→
    44→You can drag them. Resize them. Minimize them. Zoom in and out. Layer them by depth. Snap them to a grid. Undo any change. The canvas remembers where everything is, per user, per workspace.
    45→
    46→But here's what makes it more than a drawing tool:
    47→
    48→**Every node is connected to the backend.** When you drag the composer, its new position is saved to the database. When you resize the thread panel, that's persisted. When an agent spawns a new node — say, a live results panel for a streaming response — it appears on the canvas via a WebSocket event, and it stays where you put it.
    49→
    50→The canvas is not a static layout. It's a **living surface** where the interface reorganizes itself based on what you're doing, who you're talking to, and what the system needs to show you right now.
    51→
    52→---
    53→
    54→## Hot-Swappable Components: The Slot System
    55→
    56→Think of the canvas as a collection of **slots**. Each slot has a name — `chat.header`, `chat.thread`, `chat.composer`, `chat.sidebar`, `chat.actionBar`, and so on. These are the capability globals: the slots that any UI surface can fill.
    57→
    58→When you connect to a provider — say ChatGPT, or Gmail, or a custom tool — the system asks: "What components should fill these slots for *this* provider?"
    59→
    60→The answer comes from a **4-tier resolution system**:
    61→
    62→1. **Provider + variant**: If ChatGPT has a Gemini variant, use that component.
    63→2. **Provider canonical**: If not, use ChatGPT's own override.
    64→3. **Family + variant**: If the provider doesn't override, use the `ai-chat` family's version.
    65→4. **Family canonical**: Or the family's default.
    66→5. **Cross-type**: Or the universal default that works everywhere.
    67→6. **System built-in**: Or the hardcoded fallback.
    68→
    69→This means you can customize at any level. Override one slot for one provider. Override all slots for a whole family. Or let the system defaults handle everything. The resolution is automatic, deterministic, and driven entirely by data.
    70→
    71→When a new component is published — say, someone writes a better chat composer — it can be hot-swapped into any slot without touching any other code. The shell doesn't recompile. The canvas doesn't blink. The old component is gone, the new one is there, and the user never noticed the transition.
    72→
    73→---
    74→
    75→## Composable On the Fly: Agents as UI Builders
    76→
    77→This is where it gets powerful.
    78→
    79→Because the UI is data, **agents can build it**. A Vivim agent doesn't just answer questions — it can create, modify, and arrange UI components on your canvas in real time.
    80→
    81→Need a live dashboard that tracks your API usage? An agent can create a `UiComponent` row with the right HTML/CSS, assign it to a slot, and spawn a node on your canvas. It appears instantly via the WebSocket.
    82→
    83→Want to customize how a particular provider renders its results? The agent can write a provider-scoped component, publish it, and the resolution system picks it up. No human intervention needed.
    84→
    85→The canvas becomes a **programmable surface** where the interface evolves as you work. You're not just using software — you're co-creating it with your agents. They build the UI. You arrange it. They extend it. You refine it. The boundary between "user" and "builder" dissolves.
    86→
    87→---
    88→
    89→## The Conceptual Model: Family-Driven Surfaces
    90→
    91→Not every provider needs a completely different UI. An email provider and a chat provider share a lot of structural DNA — they both have a composer, a message list, a sidebar, a header. The differences are in the details: what the send button does, how threads are structured, what metadata is shown.
    92→
    93→The **conceptual model** captures this. Each provider belongs to a **family** — `ai-chat`, `email`, `messenger`, `social`, `custom`. Each family defines a **vocabulary** of primitives: the slots that are relevant to it. The `ai-chat` family might have `prompt-box`, `response-stream`, `tool-output`, `model-selector`. The `email` family might have `inbox-list`, `compose-window`, `attachment-bar`, `signature-editor`.
    94→
    95→These primitives are the building blocks. Families compose them. Providers override them. The resolution system decides which version wins.
    96→
    97→This means adding a new provider doesn't mean building a new UI from scratch. You declare its family, and the family's slot catalog and interaction grammar give you a working surface immediately. You only override what's different.
    98→
    99→---
   100→
   101→## Sandboxed, Secure, Live
   102→
   103→Every component runs in a sandboxed iframe. No inline script. No access to the parent page. Communication happens through a MessageChannel with a strict Content Security Policy. The system controls what each sandboxed component can do — which capabilities it can call, how much CPU time it gets, what network requests it can make.
   104→
   105→This isn't a restriction — it's a guarantee. Because every component is sandboxed, you can run untrusted code on the canvas without worrying about it breaking the shell. An agent can drop in a component written by a stranger, and it's safe. A provider can ship its own UI, and it can't snoop on other providers.
   106→
   107→The sandbox is invisible to the user. Components render, interact, stream results, and feel native. But underneath, they're isolated and controlled.
   108→
   109→---
   110→
   111→## Progressive Results: Streaming Into the Canvas
   112→
   113→When you send a message to an AI provider, the response doesn't appear all at once. It streams in — text blocks, thinking blocks, code blocks, citations, tool outputs, images, artifacts. Each block arrives as a `StreamBlock` with a kind and an index.
   114→
   115→The canvas renders these progressively. A `StreamingSlot` shows the response building in real time. A `ResultSlot` organizes completed blocks. You see the AI thinking, writing code, fetching data, and assembling the answer — all as live nodes on the canvas, not a static text box.
   116→
   117→This is the "progressive results" model. The interface doesn't wait for the backend to finish. It renders what's available, when it's available, where it's available. The canvas is always live.
   118→
   119→---
   120→
   121→## What This Enables (The Vision)
   122→
   123→**One screen, everything.** Chat. Email. Code. Dashboards. Agents. Projects. Knowledge bases. All on one canvas. No tab switching. No context loss. You see everything at once, arranged the way you want.
   124→
   125→**The interface is yours.** Drag nodes. Resize panels. Minimize what you don't need. Zoom into what matters. Save layouts as presets. Share them with your team. The canvas adapts to how you work, not the other way around.
   126→
   127→**Agents build the UI.** Not just answer questions — *build the interface*. Create components. Arrange nodes. Customize surfaces. The canvas is a programmable space where agents and humans co-create the experience.
   128→
   129→**New providers, instant surfaces.** Add a provider, declare its family, and you get a working UI. Override what's different. The resolution system handles the rest. No migrations. No rebuilds. Just data.
   130→
   131→**Everything is live.** WebSocket events spawn and dismiss nodes in real time. Streaming responses render block by block. Changes propagate instantly. The canvas never feels stale.
   132→
   133→**Everything is safe.** Sandboxed iframes. CSP. MessageChannel bridges. No inline script. The shell is inviolable. You can run untrusted code on the canvas without risk.
   134→
   135→---
   136→
   137→## The Technical Truth
   138→
   139→Under the hood, this is:
   140→
   141→- **Backend**: Bun + TypeScript (strict) + Prisma v6.5 (SQLite). 13 engines. A `ConceptualModelService` that resolves which component wins for which slot. A `CanvasLayerMounter` that emits spawn/dismiss events.
   142→- **Frontend**: Vite + React + @xyflow/react (React Flow). A single `CanvasSurface` component. A `UIComponentRegistry` that maps slot IDs to components. Hooks that fetch, resolve, and render.
   143→- **Data**: 54 database tables. `ProviderType` (families). `Primitive` (vocabulary). `UiComponent` (the HTML/CSS/script per slot). `UserComponentLayout` (where nodes live on the canvas). `StreamBlock` (progressive results).
   144→- **Transport**: HTTP for CRUD. WebSocket for live events. Capability-backed routes — every operation is a `UnifiedCapability` that works across CLI, UI, API, and MCP.
   145→
   146→The frontend shell is deliberately thin. It doesn't know what's inside each node. It just resolves, renders, and arranges. The richness lives in the registry, the database, and the components themselves.
   147→
   148→That's the point. The shell is **dumb** by design. The data is **smart**. And the agents are **creative**.
   149→
   150→---
   151→
   152→## In One Sentence
   153→
   154→We're building a single infinite canvas where the entire UI is database-driven, hot-swappable, sandboxed, agent-buildable, and live — so that the interface isn't something you use, it's something you **compose**, and it composes itself.

   162→# DOC 1 — PROJECT OVERVIEW & THE CANVAS VISION (vivim-final)
   163→
   164→> This is the single most important context file. Read it first. It explains what vivim-final is, what the unified canvas is, and the invariant rules you MUST NOT break when you build.
   165→
   166→## 1. What vivim-final is
   167→
   168→`vivim-final` is **cap-store v1 Knowledge Graph Rebuild** — a local-first AI conversation platform. It is NOT a generic web app; it is a capability-driven system where **every user operation is a `UnifiedCapability`** and the UI is generated from a database-backed model, not hardcoded React branches.
   169→
   170→- **Runtime:** Bun
   171→- **Language:** TypeScript (strict, ESNext, `.js` import extensions required)
   172→- **ORM:** Prisma v6.5 (SQLite)
   173→- **Frontend:** Vite + React + **@xyflow/react (React Flow)** for the canvas
   174→- **Linter:** Biome
   175→
   176→The PRIMARY frontend surface is the **unified infinite canvas** (`web/ui/src/features/canvas/CanvasSurface.tsx`). It renders every UI region as a swappable, data-driven node. A single React Flow instance IS the shell. There is no second registry — `UIComponentRegistry` IS the `nodeTypes` map.
   177→
   178→## 2. The Canvas Vision (PRD-VIVIM-CANVAS-UNIFIED-SURFACE)
   179→
   180→> "Redesign the primary user UI as an **infinite, programmable HTML canvas** where layers (chat, system, automation, agents, projects, knowledge, designer) are **swapped in on demand**. The shell is pure HTML — re-programmable by design — shipping with a robust closed set of core primitives. The canvas is an **oracle**: global access, global visibility, agentic-native, configurable by primitives."
   181→
   182→Concrete realization = the **modular UI system**:
   183→- A DB-backed **`ProviderType` (family)** conceptual model
   184→- A **`UiComponent`** node that stores hot-swappable UI code (html/css/js + sandbox), resolved through a 4-tier precedence and rendered as canvas nodes.
   185→
   186→## 3. THE INVARIANTS (never violate — these are enforced and will fail audits)
   187→
   188→1. **Frontend = Backend (5.1):** A capability/provider `slug` is the single link between backend and frontend. Render the contract + resolve slots. NEVER hardcode `if (slug === 'x')`. The POC (`html-shell-sdk-1`) violates this — it hardcodes tools/themes in React. Your build must not.
   189→2. **UI code is DATA, not code (P1):** `UiComponent` rows store html/css/sandboxJson. Surfaces are published from the DB, not compiled into the bundle.
   190→3. **Dumb shell (P2):** `CanvasSurface` is a thin React Flow host. Richness lives in `registry.resolve()`.
   191→4. **Governor Canon (P7/B1):** Only `ChromeGovernor` touches CDP. No engine imports CDP transport. The canvas layer mounter emits events only — it never touches the DOM.
   192→5. **Sandboxed (P8):** `SandboxedLayer` renders components in an iframe with a CSP. NO inline `<script>` at def-time or render-time.
   193→6. **One Entry Point (25.7):** Every operation is a `UnifiedCapability`. CLI/UI/API are thin shells over `POST /api/interpret` and `/api/capabilities/:id/execute`.
   194→7. **Store Contracts (B2):** Engines depend on `src/storage/contracts/*`, never `src/storage/impl/*`.
   195→8. **Type safety:** No `any`. Use `unknown` + narrowing. Zod at boundaries.
   196→9. **FRONTEND=BACKEND cross-surface:** A capability must resolve across CLI, API, MCP, and UI. Verify with `bun run devops verify-cross-surface`.
   197→
   198→## 4. The DB-Driven Protocol rule (P1)
   199→
   200→Provider-specific composer selectors, send methods, capture patterns, fetch URL patterns, and DOM selectors live in the DB (`ProviderEndpoint` rows, seeded from `seeds/providers/*.json`). NEVER hardcode these in TypeScript. New providers: write JSON → `bun run seed`.
   201→
   202→## 5. What the POC (`dev-poc/canvas/html-shell-sdk-1`) IS and IS NOT
   203→
   204→The POC is a **standalone Next.js 15 + React 19 + Tailwind/shadcn** playground that proves a *generic* drawing-canvas SDK: an EventBus, CommandStack (undo/redo), QuadTree (spatial index), Scene, CanvasEngine, 8 tools (select/pan/rectangle/ellipse/line/text/freehand/connection), 5 renderers, theme switcher, and a `.zip` SDK download. It is a **SOTA reference for low-level canvas rendering mechanics** (rAF loop, spatial indexing, command pattern, plugin API) — NOT a model for how vivim's UI surface works.
   205→
   206→**Gap (why we need you):** The POC knows nothing about vivim's conceptual model, capability system, DB, or React-Flow node graph. Its "canvas" is a freeform drawing board; vivim's "canvas" is a node-graph where each node is a *resolved capability/slot* rendered from `UiComponent` DB rows inside a sandboxed iframe. Your job is to bring the POC's rendering quality (smooth engine, spatial index, z-layers, tool system) INTO vivim's data-driven node canvas — without breaking the invariants above.
   207→
   208→## 6. How the stack boots (for context)
   209→
   210→- `bun run serve` starts engines only (no re-seeding, no migrate).
   211→- `bun run db:setup` = migrate + seed (first time only).
   212→- `bun run db:seed` = re-seed providers from JSON manifests.
   213→- Frontend dev server is Vite on `:5173`; backend on `:9420` (resolve via `.runtime/backend.port`).
   214→- Launch stack: `pwsh scripts/start-bg.ps1` (non-blocking). Tear down: `pwsh scripts/stop-all.ps1`.
   215→- NEVER use Playwright. Use the project's own CDP tools (`devops runtime-test engage/verify/debug`).
   216→

   218→

   220→src/

   235→Frontend import rule: ALWAYS use `@/*` path alias → `./src/*`, `.js` extension in imports, `type` imports for types, no `any`.

   247→## 2.1 L1b: Provider-Type (family) + Primitive + UiComponent (the vivim-canvas conceptual model)
   248→
   249→```prisma
   250→model ProviderType {
   251→  id                     String  @id
   252→  slug                   String  @unique   // 'ai-chat' | 'email' | 'messenger' | 'social' | 'custom'
   253→  displayName            String  @map("display_name")
   254→  description            String?
   255→  slotCatalogJson        String  @default("[]") @map("slot_catalog_json")   // ordered primitive ids
   256→  regionLayoutJson       String  @default("{}") @map("region_layout_json")  // { primitiveId: RegionRect }
   257→  interactionGrammarJson String  @default("{}") @map("interaction_grammar_json")
   258→  basePrimitive          String  @default("conversations") @map("base_primitive")
   259→  version                Int     @default(1)
   260→  createdAt              BigInt  @map("created_at")
   261→  updatedAt              BigInt  @map("updated_at")
   262→  providers        ProviderDefinition[] @relation("ProviderTypeToDefinition")
   263→  familyPrimitives Primitive[]          @relation("PrimitiveFamily")
   264→  @@map("provider_type")
   265→}
   266→
   267→model Primitive {
   268→  id                String  @id
   269→  scope             String  @map("scope")   // 'cross-type' | 'family' | 'provider'
   270→  familyId          String? @map("family_id")
   271→  providerId        String? @map("provider_id")
   272→  label             String
   273→  description       String?
   274→  defaultRegionJson String  @default("{}") @map("default_region_json")  // RegionRect JSON
   275→  version           Int     @default(1)
   276→  createdAt         BigInt  @map("created_at")
   277→  updatedAt         BigInt  @map("updated_at")
   278→  family     ProviderType?       @relation("PrimitiveFamily", fields: [familyId], references: [id], onDelete: Cascade)
   279→  provider   ProviderDefinition? @relation("PrimitiveProvider", fields: [providerId], references: [id], onDelete: Cascade)
   280→  components UiComponent[]
   281→  @@index([scope, familyId], map: "idx_prim_scope_family")
   282→  @@index([scope, providerId], map: "idx_prim_scope_provider")
   283→  @@map("primitive")
   284→}
   285→
   286→model UiComponent {
   287→  id                String  @id
   288→  primitiveId       String  @map("primitive_id")
   289→  scope             String  @map("scope")   // 'cross-type' | 'family' | 'provider'
   290→  ownerId           String  @default("global") @map("owner_id")  // familyId | providerId | 'global'
   291→  variant           String? @map("variant")  // e.g. 'gemini', 'chatgpt'
   292→  componentKey      String  @map("component_key")  // e.g. 'ai-chat.gemini.composer'
   293→  displayName       String  @map("display_name")
   294→  html              String  @default("")
   295→  css               String  @default("")
   296→  scriptUrl         String? @map("script_url")
   297→  sandboxJson       String  @default("{}") @map("sandbox_json")   // SandboxPolicy JSON (P8)
   298→  constraintsJson   String  @default("{}") @map("constraints_json")  // ComponentConstraints
   299→  contractJson      String  @default("{}") @map("contract_json")    // ComponentContract
   300→  archetype         String? @map("archetype")  // 'list'|'form'|'display'|'overlay'|'card'|'grid'
   301→  version           Int     @default(1)
   302→  status            String  @default("published")  // 'draft'|'published'|'deprecated'
   303→  author            String  @default("system")     // 'system'|'user'|'agent'
   304→  tagsJson          String  @default("[]") @map("tags_json")
   305→  defaultRegionJson String  @default("") @map("default_region_json")
   306→  createdAt         BigInt  @map("created_at")
   307→  updatedAt         BigInt  @map("updated_at")
   308→  primitive Primitive @relation(fields: [primitiveId], references: [id], onDelete: Cascade)
   309→  @@unique([primitiveId, scope, ownerId, variant])   // ONE table encodes all 4 tiers
   310→  @@index([scope, ownerId], map: "idx_uc_scope_owner")
   311→  @@index([primitiveId], map: "idx_uc_prim")
   312→  @@map("ui_component")
   313→}
   314→```

   573→## 3.5 THE 4-TIER RESOLUTION PRECEDENCE (encode this EXACTLY)
   574→
   575→```
   576→provider + variant  (scope='provider',   ownerId=providerId, variant)
   577→provider canonical  (scope='provider',   ownerId=providerId, variant=null)
   578→family  + variant  (scope='family',      ownerId=familyId,   variant)
   579→family  canonical  (scope='family',      ownerId=familyId,   variant=null)
   580→cross-type          (scope='cross-type', ownerId='global')
   581→→ system built-in default
   582→```
   583→
   584→The resolver is `UiComponentStore.resolve(ctx)` and `ConceptualModelService.resolveSurface(providerId, familyId)` (see DOC 4). A resolved slot returns `{ primitive, component, tier, fromSystemDefault }`.

   865→# DOC 7 — POC REFERENCE: html-shell-sdk-1 (mechanics to harvest, gaps to close)
   866→
   867→> The POC (`dev-poc/canvas/html-shell-sdk-1`) is a standalone Next.js 15 + React 19 + Tailwind/shadcn drawing SDK. It proves generic canvas rendering mechanics. It VIOLATES vivim invariants (hardcodes tools/themes, no React Flow, no DB). Use it as a SOTA *rendering-engine* reference, then re-express the good parts inside vivim's node model.
   868→
   869→## 7.1 What the POC gives you (HARVEST these mechanics)
   870→
   871→- **EventBus** (`src/lib/canvas-sdk/core/event-bus.ts`) — pub/sub for canvas events. Map → vivim `CapabilityEventBus` + WS forwarder.
   872→- **CommandStack** (`core/command-stack.ts`) — undo/redo command pattern. Map → frontend `useCanvasHistory.ts` (already exists, may strengthen).
   873→- **QuadTree** (`core/quad-tree.ts`) — spatial index for hit-testing/frustum culling at 10k+ nodes. Harvest the algorithm for `CanvasSurface` virtualized rendering.
   874→- **CanvasEngine** (`core/canvas-engine.ts`) — single render orchestrator, world-space → screen-space transform, transform stack (pan/zoom/world-to-screen). This is the math you want behind `CanvasDefinition.layout` (x/y/z/w/h in world space).
   875→- **8 Tools** (cursor/select, move/translate, resize, draw, erase, pan, zoom, comment) — generic interaction set. Map select/move/resize → React Flow node drag/resize; draw/erase/comment → future annotation layer (wishlist item).
   876→- **5 Renderers** (canvas2d, webgl, svg, dom, wasm-canvas) — DOM renderer is the one compatible with vivim's sandboxed `UiComponent` (html/css). webgl/canvas2d render to `<canvas>` (use for the infinite-canvas background grid / minimap, not for UI nodes).
   877→- **Theme system** (`core/theme.ts`, `ThemeTokens`) — token-driven theming. Map → vivim `ThemeProvider.tsx`; themes MUST come from DB (`UiComponent.css`) not hardcoded (POC gap: themes hardcoded).
   878→- **Zip export/import** (`export/zip.ts`) — serialize scene → zip. Map → `cap:canvas:export/import` (canvas-router already has routes).
   879→
   880→## 7.2 POC → vivim gap map
   881→
   882→| POC does | vivim needs | Action |
   883→|---|---|---|
   884→| Hardcodes 8 tools, 5 renderers, themes | Tools/renderers/themes are DATA (UiComponent) | Move tool configs into `ui_component`/`provider_type` rows; renderer chosen by archetype |
   885→| Freeform Node/Connection graph (drawing) | Conceptual, family-driven node graph | Replace POC `Scene`/`Node` with `CanvasDefinition` from resolved `UiComponent` |
   886→| Next.js 15 standalone | Vite + React + @xyflow/react in `web/ui` | Do NOT import POC; reimplement engine math in `CanvasSurface` |
   887→| No persistence | `user_component_layout` / `view_preset` tables | Use existing tables for node positions; POC zip → cap export |
   888→| No CDP/provider link | Slug is the link (frontend=backend) | POC cannot drive providers; vivim canvas nodes carry `providerSlug` |
   889→| inline script in sandboxed nodes | NEVER inline (P8 CSP) | POC's script injection model is unsafe; use `scriptUrl` + MessageChannel |
   890→
   891→## 7.3 Decision: REPLACE, not import
   892→
   893→The POC's internal `Scene`/`Node`/`Renderer` classes are incompatible with React Flow's node model and the DB-driven `UiComponent` contract. **Do not** `import` POC code into `web/ui`. Instead:
   894→1. Harvest the **math** (world→screen transform, QuadTree culling) into `CanvasSurface` helpers.
   895→2. Harvest the **CommandStack** pattern to strengthen `useCanvasHistory`.
   896→3. Harvest the **tool vocabulary** (select/move/resize/draw/erase/comment) as an interaction *catalog* stored in `provider_type.interaction_grammar_json` (data-driven, per family).
   897→4. Harvest **zip export** logic for `cap:canvas:export`.
   898→5. Discard POC's hardcoded theme/renderer registries — those belong in the DB.
   899→
   900→## 7.4 Mechanics snippet (POC coordinate model to mirror)
   901→
   902→```ts
   903→// POC CanvasEngine world→screen (mirror in CanvasSurface transform helpers)
   904→interface Transform { panX:number; panY:number; zoom:number }
   905→function worldToScreen(wx:number, wy:number, t:Transform) {
   906→  return { x:(wx - t.panX) * t.zoom, y:(wy - t.panY) * t.zoom }
   907→}
   908→// vivim CanvasDefinition.layout is world-space {x,y,z,w,h}; z = depth (not zoom)
   909→// use React Flow's own transform; only borrow QuadTree for culling offscreen nodes
   910→```

   918→# DOC 8 — TOP-5 CANVAS WISHLIST (dev-poc vs vivim gap → build targets)
   919→
   920→> Derived from comparing `html-shell-sdk-1` (rendering SOTA, zero vivim-compliance) against the vivim canvas PRD + 13-engine invariants. Each item is a concrete, wireable build target.
   921→
   922→## W1 — Data-driven tool & interaction catalog (close POC's hardest gap)
   923→**Gap:** POC hardcodes 8 tools + 5 renderers + themes. vivim must drive ALL interaction from `provider_type.interaction_grammar_json` + `ui_component`.
   924→**Build:** Extend `InteractionGrammar` (DOC 3.3) with `tools: string[]` (select/move/resize/draw/erase/comment) and `renderer: 'dom'|'canvas2d'|'webgl'`. `ConceptualModelService` exposes per-family tool/renderer set. `CanvasSurface` reads it to enable only the family-allowed tools. `useCanvasHistory` adopts POC's `CommandStack` for undo/redo of tool ops.
   925→**Wireable:** rows in `provider_type`, no migration; frontend reads `resolveFamilyForProvider`.
   926→
   927→## W2 — Infinite canvas virtualization with QuadTree culling (borrow POC math)
   928→**Gap:** POC's `QuadTree` handles 10k+ nodes; vivim `CanvasSurface` re-renders all nodes (will choke on large layouts).
   929→**Build:** Port `QuadTree` (DOC 7.1) into `web/ui/src/features/canvas/lib/quad-tree.ts`. `CanvasSurface` computes viewport bounds → queries QuadTree → mounts only visible `CanvasNode`s (keep DOM node count bounded). Off-screen nodes stay as data.
   930→**Wireable:** pure frontend lib; no backend change; respects existing `CanvasDefinition.layout`.
   931→
   932→## W3 — Sandboxed drawing/annotation layer (POC's draw/erase/comment tools, vivim-safe)
   933→**Gap:** POC has draw/erase/comment but as unsafe inline-script nodes. vivim has NO annotation surface.
   934→**Build:** A new `UiComponent` archetype `'overlay'` (or `prim:cross-type:annotation`) rendering a `<canvas>` (DOM renderer) inside `SandboxedLayer` (POC-safe: `scriptUrl` + MessageChannel, `allowInlineScript:false`). Strokes stored as `StreamBlock` (kind `'artifact'`) or `view_preset.layout_json`. Draw/erase/comment tools enabled per W1 catalog.
   935→**Wireable:** new `ui_component` row + `cap:canvas:mutate` payload for strokes.
   936→
   937→## W4 — Live layer streaming over `/ws/canvas` (finish PRD C7)
   938→**Gap:** `CanvasLayerMounter.spawn()` emits `canvas:layer:spawned` on the event bus, but `registerCanvasLayerForwarder` + `useCanvasEvents` WS path is PENDING. POC has a working EventBus but no cross-tab sync.
   939→**Build:** Implement `registerCanvasLayerForwarder(eventBus)` in `websocket.ts` (mirror `registerCanvasMutationForwarder`). `useCanvasEvents` already subscribes — verify it mounts/dismisses nodes on WS message. This makes spawned layers appear in all open browsers instantly.
   940→**Wireable:** backend WS forwarder + existing frontend hook; no schema change.
   941→
   942→## W5 — Progressive result rendering from StreamBlock (finish PRD C6)
   943→**Gap:** `GET /api/conversations/:id/stream-blocks` is NOT implemented; `useStreamBlocks` hook has no backend. POC has no streaming at all.
   944→**Build:** `conversation-router.ts` → `cap:conversation:stream_blocks` returning `ContentBlock[]` from `StreamBlock` rows (keyed by `blockIndex`/`blockKind`), falling back to wrapping `ConversationMessage.content` as one `text` block. `useStreamBlocks` consumes it; `StreamingSlot`/`ResultSlot` render progressively (text/thinking/code/artifact/image/citation/tool_use).
   945→**Wireable:** new router route + capability + existing frontend hook/components.
   946→
   947→## Wishlist summary (priority order)
   948→1. W4 — WS live layers (highest value, finishes a PENDING PRD item, pure integration)
   949→2. W5 — Stream-blocks endpoint (finishes PENDING PRD C6, unblocks progressive UI)
   950→3. W2 — QuadTree virtualization (scalability, pure frontend)
   951→4. W1 — Data-driven tool catalog (closes POC's core gap, family-driven)
   952→5. W3 — Sandboxed annotation layer (new surface, uses W1+W2)
