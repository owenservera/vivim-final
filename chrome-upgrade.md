Thought Process

Below is the same 11-phase skeleton, re-grounded against the actual codebase in `chrome-slave-architecture.md`. Every phase is now tied to specific files, types, invariants, and a PR-level breakdown. The **Governor Canon (B1)** is preserved throughout: `ChromeGovernor` remains the sole I/O authority — every new abstraction (`BrowserRuntime`, `BrowserActor`, `EventBus`, `Pool`, `Scheduler`) is either a Governor-internal module or a delegate that routes CDP back through the Governor.

---

## Cross-cutting rules (apply to every phase)

1.  **B1 invariant**: no engine outside `chrome-governor.ts` may hold a `CDPTransport` reference. New subsystems call `governor.executeCdpMethod(...)` or a Governor-exposed helper.
2.  **Each phase = N small PRs**, each shippable behind a feature flag in `src/config.ts` (e.g. `CAP_STORE_PHASE2_BROWSER_RUNTIME`).
3.  **Each PR adds a test** in `tests/engines/<phase>/` and updates the Phase-0 bench harness.
4.  **Rollback = flip flag**. No PR may delete the old code path until the next phase proves the new one in prod for ≥ 7 days.
5.  **DB migrations are additive only** — new columns nullable, new tables separate. Backfill in a sub-PR; drop-old in a later phase.

# Phase 2 — Runtime Refactor (2–3 weeks)

**Objective**: Extract `BrowserRuntime` as a Governor-internal module. Governor keeps its public API; CDPProxy / HealthMonitor / CdpWatchdog move _inside_ `BrowserRuntime`. B1 preserved: `BrowserRuntime` is not a peer of Governor — it is a private collaborator.

## Scope

-   New: `src/engines/runtime/browser-runtime.ts`, `runtime/cdp-proxy.ts`, `runtime/health.ts`, `runtime/watchdog.ts`, `runtime/state.ts`
-   Edit: `chrome-governor.ts` (delegate to `BrowserRuntime`), `cdp-watchdog.ts` (move), `chrome-governor.ts` HealthMonitor inner class (move)
-   No change: `fleet-supervisor.ts`, `launcher.ts`, `cdp-transport.ts`, `profile-allocator.ts`

## Target shape

text

ChromeGovernor (public API unchanged)

└─ BrowserRuntime

├─ CDPProxy (moved from governor inner class)

│ ├─ per-slave AsyncMutex

│ ├─ ensureConnected

│ └─ harness DAG executor

├─ HealthMonitor (moved from governor inner class)

├─ CdpWatchdog (moved from cdp-watchdog.ts)

├─ ReconnectManager (extracted from BunCdpClient auto-reconnect)

├─ MetricsSink (Phase 1)

└─ SlaveStateStore (wraps instanceMap + DB)

## PR sequence

### PR 2.1 — Extract `SlaveStateStore`

Move `instanceMap` and slave-state transitions out of `FleetSupervisor` into `SlaveStateStore`. `FleetSupervisor` delegates. Enforces the §13 state machine via `nextState()` (already in `slave-states.ts`). No behavior change.

### PR 2.2 — Move `CDPProxy` into `BrowserRuntime`

The proxy is currently "rebuilt on every access" (§6). Replace with a cached `BrowserRuntime.for(slaveId)` that lazily builds and invalidates on state change. Public Governor methods (`evaluate`, `executeCdpMethod`, `captureScreenshot`, `runHarnessPlan`) delegate.

### PR 2.3 — Move `HealthMonitor` + `CircuitBreaker`

Circuit-breaker logic stays in DB (`CircuitBreakerStateRow`) — no schema change. The monitor becomes a `BrowserRuntime` component with a single `tick()` method.

### PR 2.4 — Move `CdpWatchdog`

Already a separate file (`cdp-watchdog.ts`). Move into `runtime/watchdog.ts` and have `BrowserRuntime.ensureConnected` wire it. No logic change.

### PR 2.5 — Extract `ReconnectManager`

`BunCdpClient` has auto-reconnect (§7.1). Pull the policy (exp backoff, max 3) into `ReconnectManager` so Phase 9 can swap strategies per failure class.

## API delta

typescript

// New internal type

class BrowserRuntime {

for(slaveId: string): BrowserSession; // throws if not running

acquire(slaveId: string): Promise<BrowserSession\>; // lazy connect

release(slaveId: string): void;

tick(): Promise<void\>; // health probe all

shutdown(): Promise<void\>;

}

interface BrowserSession {

readonly slaveId: string;

readonly state: SlaveState;

cdp: CDPProxy;

watchdog: CdpWatchdog;

}

`ChromeGovernor` keeps the _exact_ public API from §6. Internal call sites change from `this._cdpProxy(...)` to `this._runtime.for(slaveId).cdp...`.

## Compatibility / rollback

-   Flag `CAP_STORE_PHASE2_BROWSER_RUNTIME`. Off = old code path.
-   Both paths share the same `SlaveStateStore` after PR 2.1, so flipping back is safe.

## Tests / gates

-   Existing harness tests pass unchanged (proves API parity).
-   New: `BrowserRuntime.for(slaveId)` returns same instance within a state epoch, new instance after `running → stopped → starting`.
-   KPI gate: CDP p99 regression <2%.

## Exit criteria

-   `chrome-governor.ts` contains zero CDP logic — only orchestration (spawn routing, capability resolution, harness dispatch).
-   Governor file LOC drops by ≥40%.
-   B1 still holds: no new exports of `CDPTransport`.

# Phase 3 — Actor Model (2 weeks)

**Objective**: Each browser becomes an autonomous `BrowserActor` with a mailbox. Governor becomes a _supervisor_ of actors, not a direct CDP driver.

## Scope

-   New: `src/engines/actor/{browser-actor.ts, mailbox.ts, messages.ts, supervisor.ts}`
-   Edit: `chrome-governor.ts` (public methods become message posts), `fleet-supervisor.ts` (spawn now creates an actor)

## Design

### 3.1 Mailbox

typescript

class Mailbox<M\> {

private q: AsyncQueue<M\>;

async post(m: M): Promise<void\>;

async next(): Promise<M\>;

depth(): number;

}

Backed by a promise queue. The existing per-slave `AsyncMutex` in `CDPProxy` becomes redundant — the mailbox serializes.

### 3.2 Message types (`messages.ts`)

typescript

type ActorMsg \=

| { t: 'EnsureRunning' }

| { t: 'Evaluate'; expr: string; k: (r: unknown) => void }

| { t: 'CdpMethod'; method: string; params: unknown; k: (r: unknown) => void }

| { t: 'Harness'; dag: HarnessDAG; k: (r: HarnessResult) => void }

| { t: 'Screenshot'; region?: Region; k: (r: string) => void }

| { t: 'HealthProbe'; k: (ok: boolean) => void }

| { t: 'Shutdown'; k: () => void }

| { t: 'Crash'; cause: FailureClass } // internal, from watchdog

| { t: 'Recover'; strategy: RecoveryStrategy }

### 3.3 `BrowserActor`

typescript

class BrowserActor {

constructor(slaveId, runtime: BrowserRuntime, mailbox: Mailbox<ActorMsg\>);

start(): void; // begins consume loop

async handle(m: ActorMsg): Promise<void\>; // dispatches to runtime

state(): SlaveState;

ask<T\>(m: ActorMsg & { k: (T) => void }): Promise<T\>; // post + await callback

}

The actor owns: lifecycle, watchdog subscription, health probe scheduling, recovery. **State isolation**: no actor reads another actor's `BrowserSession`.

### 3.4 `ActorSupervisor` (replaces parts of `FleetSupervisor`)

Holds `Map<slaveId, BrowserActor>`. `FleetSupervisor.spawn` becomes: launch Chrome → create actor → actor.start(). `FleetSupervisor.killAll` → broadcast `Shutdown`.

## PR sequence

### PR 3.1 — Introduce `Mailbox` + `ActorMsg` types (no callers yet)

Pure additive. Unit-test the queue.

### PR 3.2 — Wrap `BrowserRuntime` calls in actor handlers

`BrowserActor.handle` calls into `BrowserRuntime.for(slaveId)`. No Governor change yet.

### PR 3.3 — Route `evaluate`, `executeCdpMethod`, `captureScreenshot` through actor mailbox

Governor methods become `actor.ask({ t: 'Evaluate', ... })`. Behind flag.

### PR 3.4 — Route `runHarnessPlan` through actor

The DAG executor moves into `BrowserActor.handle({ t: 'Harness' })`. Topological sort (§19) unchanged.

### PR 3.5 — Route lifecycle (`ensureRunning`, `recoverAuth`) through actor

`EnsureRunning` and `Recover` messages. `recoverAuth` (§15) now an actor-internal strategy.

### PR 3.6 — Remove per-slave `AsyncMutex` from `CDPProxy`

Mailbox is the serialization layer. Delete mutex code path (flag-protected removal).

## Compatibility / rollback

-   Flag `CAP_STORE_PHASE3_ACTORS`. Each PR adds a route; flipping back restores the direct-call path.
-   Public Governor API unchanged — callers (harness, conversation engine) unaffected.

## Tests / gates

-   Concurrency test: 100 parallel `evaluate` calls on one slave serialize correctly (no interleaving in `TraceEntry`).
-   Isolation test: actor A's `BrowserSession` reference never appears in actor B's trace.
-   KPI gate: CDP p99 regression <3% (mailbox overhead).

## Exit criteria

-   `FleetSupervisor` contains no CDP logic and no direct `BrowserRuntime` calls — only actor supervision.
-   No cross-actor state mutation (verified by a lint rule banning `BrowserSession` imports outside `BrowserActor`).
-   B1 holds: actors hold a `BrowserRuntime` ref, never a raw `CDPTransport`.

### 4.4 Warm startup

`WarmSpawner` runs at boot (after `FleetSupervisor` init) and on a 30s tick. It pre-launches Chrome with a temp profile, navigates to `about:blank`, and leaves the CDP connection open. On `acquire`, the pool swaps the profile via `Target.createTarget` + cookie injection (faster than full restart) **or** destroys + respawns if provider needs a real profile dir.

> Note: profile swap is not always possible (SingletonLock, §4). For provider-specific slaves, the pool keeps a per-provider warm set with pre-allocated profile dirs.

## PR sequence

### PR 4.1 — `BrowserPool` skeleton with generic-pool semantics, no warm spawn yet

Pool wraps `FleetSupervisor.spawn` / `kill`. Lease = opaque handle.

### PR 4.2 — Warm spawner for provider-free browsers

Replaces `ensureGenericBrowser()` memoization. `killAll()` now drains pool.

### PR 4.3 — Per-provider warm pool

Pre-allocate profile dirs via `ProfileAllocator.allocate` for the top 3 providers by usage (query `ProviderAccount` counts). Warm Chrome with that profile.

### PR 4.4 — Lease recycling

On `release`, run a cheap health check (`Browser.getVersion`). If pass and not expired → return to warm set. Else → `killChrome` and decrement.

### PR 4.5 — Pool metrics

`chrome_pool_size{provider}`, `chrome_pool_leases_total`, `chrome_pool_warm_hits_total` / `misses_total`.

## Compatibility / rollback

-   Flag `CAP_STORE_PHASE4_POOL`. Off = current `ensureGenericBrowser` path.
-   Pool never bypasses `FleetSupervisor` admission control (§5) — it sits _above_ it. A `FleetLimiter.acquire()` failure still throws `FleetQueueFullError`.

## Tests / gates

-   Warm-hit benchmark: 100 acquires, target ≥80% warm hits after steady state.
-   Cold-spawn fallback: when pool empty, spawn latency = baseline (no regression).
-   KPI gate: spawn p95 reduced ≥70% (Phase 0 target).

## Exit criteria

-   Average startup reduced by ≥70% (measured via `FleetEvent` deltas).
-   `ensureGenericBrowser` deleted; all callers go through pool.
-   No profile corruption from recycling (cookie-file truth check, §14, still passes).

### 5.2 Scheduler

typescript

class BrowserScheduler {

enqueue(q: QueueName, task: Task): Promise<TaskResult\>;

cancel(taskId: string): void;

snapshot(): SchedulerSnapshot;

}

-   **Priority**: `input` > `network` > `dom` > `runtime` > `screenshot` (configurable).
-   **Fairness**: weighted round-robin across non-empty queues; no starvation (aging after 500ms wait).

-   **Backpressure**: when total in-flight > `maxInFlight` (default 8), `enqueue` awaits a slot (with timeout → `SchedulerBackpressureError`).

}

## Design

### 6.1 `PressureFeed`

Unify today's `SystemPressure` (§5) + Phase-0 `/json/process-info` polling. Exposes:

typescript

interface Pressure {

cpuPct: number; // per-core, not loadavg

memPct: number;

gpuMemPct?: number; // from chrome://gpu or /json/process-info

chromeRssTotal: number; // sum across slaves

rendererCount: number;

fdUsagePct?: number; // Unix only

}

Poll cadence: 5s (cheaper than 30s health probe; Phase 1 metrics cover it).

### 6.2 `AdaptiveLimiter`

Replaces `FleetLimiter`. `maxConcurrent` becomes a function of pressure:

text

if cpuPct > 80 → maxConcurrent = max(1, current - 1)

if cpuPct < 50 and queueDepth > 0 → maxConcurrent = min(ceiling, current + 1)

Hysteresis: ±5% band, no oscillation faster than 30s. Persists decisions to `FleetEvent('concurrency_adj')`.

-   `GpuAllocator` (new): pins heavy slaves to GPU process or disables GPU per slave based on `chromeRssTotal` and provider need (e.g. screenshot-heavy providers).

### 6.4 Browser prioritization

When under load, prefer slaves with active conversations (query `HarnessCommand` recent activity). Low-priority slaves (idle > 10 min) are eligible for eviction to warm pool.

## PR sequence

### PR 6.1 — `PressureFeed` (replaces `SystemPressure`)

Existing `cpuOverloadPct`/`memOverloadPct` thresholds (§17) become guard rails, not the only signal.

### PR 6.2 — `AdaptiveLimiter`

# Phase 10 — Scale-Out Architecture (3–4 weeks)

**Objective**: Break the single-machine assumption. Governor → Fleet Manager → Worker Nodes → Browser Actors.

## Scope

-   New: `src/fleet/{fleet-manager.ts, worker-node.ts, worker-protocol.ts, remote-cdp.ts, distributed-scheduler.ts}`
-   Edit: `ChromeGovernor` (becomes Fleet Manager facade), `BrowserActor` (becomes remote-able)

## Design

### 10.1 Topology

text

ChromeGovernor (single, stateless facade)

└─ FleetManager (owns global SlaveRegistry, schedules across workers)

├─ WorkerNode A (local) → BrowserActor ×N

├─ WorkerNode B (remote) → BrowserActor ×N

└─ WorkerNode C (remote) → BrowserActor ×N

### 10.2 Worker protocol

WebSocket-based JSON-RPC (or gRPC if perf demands). Methods:

-   `Spawn(providerId, accountId, opts) → slaveId`
-   `Kill(slaveId)`
-   `CdpSend(slaveId, method, params) → result`
-   `Subscribe(slaveId, event) → stream`
-   `Health(slaveId) → status`
-   `Drain() → ack`

Worker nodes run a slim binary (`cap-store-worker`) that owns `FleetSupervisor` + `BrowserActor` set + local `BrowserRuntime`. Chrome processes live on the worker, not the manager.

### 10.3 Remote CDP

Two options:

-   **Tunneled** (default): worker proxies CDP WebSocket through worker-protocol `CdpSend`. Keeps B1 trivially (manager never sees raw WS).
-   **Direct** (opt-in): worker exposes Chrome's debug port via SSH tunnel or mTLS; manager's `CDPTransport` connects directly. Lower latency, more exposure. Flag `CAP_STORE_REMOTE_CDP_MODE=tunneled|direct`.

### 10.4 Distributed scheduler

`FleetManager` picks worker for a new slave based on:

1.  Affinity: same provider+account → same worker (warm profile already there).
2.  Load: `PressureFeed` (Phase 6) reported per worker.
3.  GPU availability per worker.
4.  Geographic proximity (future).

Rebalancing: live migration is _not_ supported in Phase 10 (Chrome state is non-portable). Eviction + re-spawn on another worker is.

### 10.5 Kubernetes

-   `cap-store-manager` Deployment (1 replica, leader-elected).
-   `cap-store-worker` DaemonSet or Deployment (scaled by KEDA on `chrome_pool_queue_depth`).
-   Profile dirs on PVC per worker (StatefulSet for sticky accounts).
-   CDP debug ports never exposed outside the pod network.

### 10.6 Failure modes

-   Worker disconnect → FleetManager marks all its slaves `unknown` → after 60s, marks `crashed` → Phase 9 recovery on another worker.
-   Manager failover (leader election) → new leader reads `FleetEventStream` (Phase 7) to rebuild global state.

## PR sequence

### PR 10.1 — `WorkerProtocol` interface + in-process worker

Single worker = local. Proves the abstraction.

### PR 10.2 — `FleetManager` + multi-worker registry

Still local only, but Governor delegates to FleetManager.

### PR 10.3 — Remote worker (WebSocket transport)

Two-process setup: `bun run cap-store-worker` + `bun run cap-store-manager`.

### PR 10.4 — Remote CDP (tunneled mode)

`CDPTransport` becomes transport-agnostic: `LocalCdpTransport` (today) vs `RemoteCdpTransport`.

### PR 10.5 — Distributed scheduler (affinity + load)

`FleetManager.spawn` picks worker.

### PR 10.6 — Kubernetes manifests + autoscaling

Helm chart, KEDA ScaledObject, PVC templates.

### PR 10.7 — Manager HA (leader election via Postgres advisory lock or etcd)

Single-writer FleetManager; workers connect to leader.

## Compatibility / rollback

-   Flag `CAP_STORE_PHASE10_DISTRIBUTED`. Off = single-worker local mode (today's behavior).
-   `ChromeGovernor` API unchanged — callers (harness, conversation engine) don't know about workers.

## Tests / gates

-   2-worker integration: kill worker A → slaves respawn on B within 60s.
-   200-browser load test across 4 workers.
-   Manager failover: kill leader → new leader elected in <10s, no orphan slaves.
-   KPI gate: spawn p95 across workers < 2× single-machine baseline.

## Exit criteria

-   Architecture is not limited to a single machine.
-   `ChromeGovernor` runs statelessly; all state in DB + workers.
-   B1 holds: only workers hold `CDPTransport`; manager proxies.

**Exit Criteria**: Every CDP command is traceable end-to-end. Dashboards deployed. Observability overhead <2%.

---

### Phase 2 — Runtime & Domain Refactor (2–3 weeks)

**Objective**: Extract `BrowserRuntime` (mechanics) and `Domain` (business) from the Governor.

**Scope**:

-   New: `src/domain/` (Slave, Lease, Provider interfaces).
-   New: `src/engines/runtime/browser-runtime.ts` (and sub-modules).
-   Edit: `chrome-governor.ts` (delegates to Domain, which delegates to Runtime).

**Key Decisions**:

-   **ADR-0002**: BrowserRuntime abstraction.
-   **ADR-0003**: Domain Layer isolation.

**PR Sequence**:

1.  Extract `SlaveStateStore` (state machine logic).
2.  Extract `CDPProxy` into `BrowserRuntime`.
3.  Extract `HealthMonitor` & `CircuitBreaker`.
4.  Extract `ReconnectManager` (policy separated from `BunCdpClient`).
5.  Move provider/account resolution into `Domain`.

**Remote-Readiness**: `BrowserRuntime` implements `IBrowserRuntime` which accepts a `BrowserEndpoint` (local port, WS URL, or future remote address).

**Exit Criteria**: Governor contains zero CDP logic. Runtime contains zero provider logic.

---

### Phase 3 — Actor Model (2 weeks)

**Objective**: Each browser becomes an autonomous `BrowserActor` with a mailbox.

**Scope**: New `src/engines/actor/`.

**Key Decisions**:

-   **ADR-0004**: Browser Actors & Mailbox pattern.

**Changes**:

-   `Mailbox<M>`: Async queue replacing per-slave `AsyncMutex`.
-   `BrowserActor`: Owns lifecycle, health, and recovery. State isolation enforced—actors never reference each other's `BrowserSession`.
-   `ActorSupervisor`: Replaces lifecycle management in `FleetSupervisor`.

**Exit Criteria**: Governor methods are `actor.ask(...)` posts. `AsyncMutex` deleted. CDP p99 regression <3%.

---

### Phase 4 — Browser Pooling (1–2 weeks)

**Objective**: Eliminate cold startup via warm pools.

**Scope**: New `src/engines/pool/`.

**Key Decisions**:

-   **ADR-0005**: Pinned vs. Ephemeral pools. (Reject profile swapping due to fragility).

**Changes**:

-   **Ephemeral Pool**: Reusable, provider-free browsers (e.g., generic web automation). Pre-warmed.
-   **Authenticated Pool**: Pinned 1:1 to a `(provider, account)`. If killed, destroyed and re-spawned fresh. No session reuse across identities.
-   `Lease` lifecycle managed by Domain Layer.

**Exit Criteria**: Generic spawn p95 reduced >70%. No profile corruption. `ensureGenericBrowser` deleted.

---

### Phase 5 — Resource-Class Scheduler (2 weeks)

**Objective**: Replace single-mailbox execution with dependency-aware resource scheduling.

**Scope**: New `src/engines/scheduler/`.

**Key Decisions**:

-   **ADR-0006**: Resource Classes over dumb queues.

**Changes**: Instead of fixed queues, the scheduler understands **Resource Classes**:

`DOM`

-   Backpressure via `maxInFlight` (default 8) and `AbortSignal` timeouts.

**Exit Criteria**: Read-heavy DAGs execute 3x faster. No DOM races (exclusive enforcement verified by traces).

---

### Phase 6 — Adaptive Resource Manager (2 weeks)

**Objective**: Turn the fleet into a self-managing system based on host pressure.

**Scope**: New `src/engines/resource/`.

**Changes**:

-   `PressureFeed`: Unifies `SystemPressure` + `/json/process-info` (5s poll).
-   `AdaptiveLimiter`: `maxConcurrent` scales up/down based on CPU/Mem hysteresis bands.
-   `GpuAllocator`: Dynamically sets `disableGpu` on spawn based on `chromeRssTotal`.
-   Eviction: Idle slaves (>10m) returned to Phase 4 warm pool.

**Exit Criteria**: Fleet adapts to 90% CPU load within 30s. Static `cpuOverloadPct` deprecated.

---

### Phase 7 — Event Bus (2–3 weeks)

**Objective**: Formalize implicit event flows into a typed, in-process bus. (No event sourcing yet).

**Scope**: New `src/engines/events/event-bus.ts`.

**Changes**:

-   Typed events: `SlaveSpawned`, `SlaveCrashed`, `CircuitOpened`, etc.
-   In-process async iterator bus.
-   Existing `FleetEventRow` DB writes converted to bus subscribers.
-   **No replay, no event store.** Just decoupled publish/subscribe.

**Exit Criteria**: No direct `createFleetEvent` calls outside the DB subscriber. Lifecycle decoupled.

---

### Phase 8 — Provider Platform & Replay (2 weeks)

**Objective**: Convert providers to plugins. Add event replay capability.

**Scope**:

-   New: `src/engines/providers/` (plugin interface).
-   New: `src/engines/events/replay.ts`.

**Changes**:

-   **ADR-0007**: Provider Plugin Architecture.
-   `ProviderPlugin` interface (URLs, selectors, typing, anti-detection, recovery hooks).
-   Migrate `chatgpt`, `claude`, `gemini` to plugins.
-   **Event Replay**: Introduce `rebuildSlaveState(slaveId)` that reads the existing DB `FleetEvent` table to reconstruct state (preparation for Phase 10 failover).

**Exit Criteria**: Adding a provider requires zero core code changes. Replay accurately rebuilds state from DB history.

---

### Phase 9 — Reliability & Event Store (2–3 weeks)

**Objective**: Failure-class-specific recovery. Introduce the append-only Event Store.

**Scope**:

-   New: `src/engines/reliability/`.
-   New: `src/engines/events/event-store.ts`.

**Changes**:

-   `FailureClassifier` (OOM, RendererCrash, AuthFailure, CdpDisconnect, etc.).
-   `RecoveryOrchestrator` subscribes to `SlaveCrashed` and applies class-specific strategies (e.g., `AuthFailure` → visible relaunch; `CdpDisconnect` → force reconnect).
-   **Event Store**: New append-only `FleetEventStream` table. The old `FleetEventRow` becomes a projection.

**Exit Criteria**: Uniform failure counter removed. Restart frequency reduced >50%. Event Store populated.

---

### Phase 10 — Scale-Out & Event Sourcing (3–4 weeks)

**Objective**: Break the single-machine assumption. Full event sourcing for distributed state.

**Scope**:

-   New: `src/fleet/` (FleetManager, WorkerNode, RemoteCdp).
-   New: `src/engines/events/sourcing.ts`.

**Changes**:

-   **ADR-0008**: Distributed Fleet Topology.
-   `ChromeGovernor` becomes a stateless facade for `FleetManager`.
-   `WorkerNode` runs `FleetSupervisor` + `BrowserActor` set.
-   **Remote CDP**: `BrowserRuntime` (from Phase 2) finally utilizes its remote endpoint capability. Tunneled via worker protocol.
-   **Event Sourcing**: `FleetManager` leader election reads `FleetEventStream` (Phase 9) to rebuild global state on failover.
-   KEDA autoscaling on `chrome_pool_queue_depth`.

**Exit Criteria**: Architecture is not limited to one machine. Manager failover <10s. 200-browser load test passes across 4 workers.

---

### Phase 11 — Production Hardening (Continuous)

**Objective**: Enterprise readiness and SLO attainment.

**Deliverables**:

-   Chaos testing suite (kill Chrome, drop WS, fill disk).
-   Load/Stress/Leak testing (24h soak, <10% RSS growth).
-   Security review (mTLS on worker protocol, Vault integration for credentials, `--remote-debugging-pipe`).
-   SLO Dashboards (Spawn p95 <5s, DAG success ≥95%, Uptime ≥99.5%).
-   Runbooks for every Phase 9 failure class.

**Exit Criteria**: 30 consecutive days of SLO attainment. Security sign-off.

---

### Phase 12 — Legacy Removal & Deprecation (1–2 weeks)

**Objective**: Eliminate technical debt accrued during the incremental refactor.

**Scope**: Global codebase cleanup.

**Changes**:

-   **ADR-0009**: Legacy Code Purge.
-   Remove all `CAP_STORE_PHASE<N>_*` feature flags (Phase 2 through 10).
-   Delete obsolete code paths (`provider-selectors.ts`, old `FleetSupervisor` logic, old `FleetEventRow` table if fully replaced by Event Store).
-   Simplify interfaces now that single-machine assumptions are gone.
-   Update all `docs/` to reflect the final architecture, removing "old vs. new" comparisons.

**Exit Criteria**: No dead code. No feature flags. Interface signatures reflect pure target architecture. Binary size reduced by >5% from flag removal.
