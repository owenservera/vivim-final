## GAP-5 (Critical) — Server crashes on boot: Prisma SQLite WAL init uses wrong raw query method

- **Severity:** P0 (system cannot start)
- **Invariant:** Phase Gates; system must boot for any capability testing
- **Observed:** On `vivim serve` (boot via `createServerWithEngines` → kernel bootstrap), the
  Prisma WAL initialization tries `prisma.$executeRawUnsafe()` with a query that returns
  results. SQLite bans this: "Execute returned results, which is not allowed in SQLite."
- **Error signature:**
  ```
  PrismaClientKnownRequestError (P2010):
  Raw query failed. Code: `N/A`.
  Message: `Execute returned results, which is not allowed in SQLite.`
  ```
- **Root cause:** The WAL (Write-Ahead Log) init code in `src/storage/prisma.ts` (or the
  call site in `initPrismaWal`) uses `$executeRawUnsafe` for a query that selects/returns
  rows. SQLite via Prisma requires `$queryRawUnsafe` for queries that return results and
  `$executeRawUnsafe` only for INSERT/UPDATE/DELETE.
- **Fix direction:** Replace `$executeRawUnsafe` with `$queryRawUnsafe` at the WAL init
  call site, or add `.then(() => {})` to consume results if using `$executeRaw`.
- **Impact on probe suite:** All server-dependent tests (T1 coverage, T3 runtime coverage,
  T5 resolve speed) return "server not reachable" — the coverage gap measurement is
  reported as `0.0%` (no caps reachable via CLI when server is down). Full gap quantification
  requires GAP-5 to be fixed first.

## GAP-1 — Product CLI `help` only surfaces `cli`-surface capabilities

- **Severity:** P0
- **Invariant:** "Every operation is a `UnifiedCapability`. CLI and frontend are thin NL
  shells." (AGENTS.md §One Entry Point)
- **Observed (from code audit):** `vivim help` / `vivim` (no args) reaches the server via
  `fetchCliCapabilities(remote)` → `GET /api/capabilities?surface=cli`
  (`src/cli/commands/registry-bridge.ts:119-123`). The `surface=cli` filter means only
  capabilities registered with `surfaces: ['cli', ...]` appear.
- **Test:** `two-command-ceiling.test.ts` measures `reachable/universe` coverage (currently
  0.0% due GAP-5); `right-data-coverage.test.ts` reports the delta.
- **Impact:** An agent running the two-command ceiling (`serve` + `help`) cannot "know
  everything" — it sees only a subset of the system.
- **Fix direction:** Either expose a `vivim capabilities [--surface=all]` command that
  calls `GET /api/capabilities` without the surface filter, or add a `cli` surface alias
  to introspection capabilities.

## GAP-2 — Non-`cli` capabilities have no product-CLI path

- **Severity:** P0
- **Invariant:** One Entry Point; "New capability? Register ... a `*caps.ts` module."
  (AGENTS.md §Adding a Capability)
- **Observed (from code audit):** Capabilities exposed only to `ui`/`api`/`mcp`/`workflow`
  surfaces are registered in `UnifiedCapabilityRegistry` but never bridged to the
  `CommandRegistry` (`syncCliFromUnified` only iterates `reg.list({ surface: 'cli' })`,
  `src/cli/commands/registry-bridge.ts:64`).
- **Test:** `right-data-coverage.test.ts` documents coverage < 100% (0.0% when server down).
- **Impact:** The "two commands to know everything" goal fails for every non-cli surface.
- **Fix direction:** Auto-bridge all surfaces to the CLI command tree, or add an explicit
  introspection capability on every surface.

## GAP-3 — Kernel oracle is server-only, no product-CLI binding

- **Severity:** P1
- **Invariant:** One Entry Point (single call should surface topology+health+capability+config)
- **Observed:** `POST /api/kernel/oracle/query {op:"all"}` (kernel-router.ts:52) is the only
  true single-call full-system introspection. It has **no `cliCommand`** binding — unreachable
  through the product CLI under the CLI-only constraint.
- **Test:** `oracle-single-call.test.ts` confirms no `oracle`/`kernel`/`topology` command
  appears in `vivim help`.
- **Impact:** The one canonical "know everything in one call" path is not available to a
  CLI-only agent. `devops runtime-test discover --offline` partially fills this but is a
  separate tooling surface, not the product CLI.
- **Fix direction:** Register an `nlcl:kernel_oracle` capability with `surfaces: ['cli','api']`
  whose handler calls `oracle.query({type:'all'})`.

## GAP-4 — NL interpret has no product-CLI entry

- **Severity:** P2
- **Invariant:** Cross-surface parity ("Add `cliCommand`, `ui`, and `mcpToolName`")
  (AGENTS.md §Adding a Capability)
- **Observed:** `POST /api/nlcl/interpret` (nlcl-router.ts) resolves natural-language phrases
  to capabilities, but no product-CLI command (`interpret`/`ask`/`natural`) is registered.
- **Test:** `nl-resolve-speed.test.ts` records absence of an NL entry in `vivim help`.
- **Impact:** The "fastest path to the right data when you don't know the command name"
  (NL) is unavailable through the product CLI.
- **Fix direction:** Bridge `registerNlInterpretCapability` output to a `cliCommand`
  (`vivim ask "<phrase>"`).
