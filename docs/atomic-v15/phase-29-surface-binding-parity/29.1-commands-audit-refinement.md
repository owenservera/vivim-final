# 29.1 — commands-audit-refinement

**Depends:** 27.1, 28.1 · **Phase:** 29 · **Closes:** false-positive portion of AR-0019…AR-0063 (P2 potential-new)

## Intent
The `commands` pass currently flags **any** capability without an NL catalog entry as "potential new
command" (P2), even when the capability is already invocable via `cliCommand` / `apiEndpoint` / `ui` / `mcp`.
That is a false positive against the single-command-layer invariant: NL is one of several surfaces, and a
capability reachable via CLI/API is command-surface-complete.

## Fix (in `devops/audit-arch/passes/commands.ts`)
1. While extracting each capability definition, also capture binding presence from the object text:
   `hasCli` (`cliCommand`), `hasApi` (`apiEndpoint`), `hasUi` (`ui:`), `hasMcp` (`mcpToolName`).
2. A capability is `bound` if it has an NL catalog entry OR `hasCli` OR `hasApi` OR `hasUi` OR `hasMcp`.
3. "Potential new command" (P2) fires **only when** a capability declares an *interactive* surface
   (`cli` | `ui` | `workflow` | `mcp`) AND is **not** `bound`. API-only/internal capabilities are not flagged.
4. Keep "Dangling" (P1), "Surface declared but not bound" (P2), and "Central command candidate" (P2) rules
   unchanged.

## Store Contract
- Audit-only; no runtime change.
