# 26.1 — cap:help

**Depends:** none · **Phase:** 26 · **Closes:** AR-0004 (P1 dangling `cap:help`)

## Intent
`help` is a top-priority NL pattern (`catalog.ts`) but `cap:help` is never registered. Implement it as a
real, user-facing capability that returns the available commands grouped for the requesting surface.

## Interface
```ts
makeCapability(
  {
    id: 'cap:help',
    slug: 'help',
    name: 'Help',
    description: 'Show available commands and capabilities for the current surface.',
    category: 'system',
    inputSchema: { type: 'object', properties: { surface: { type: 'string' } } },
    outputSchema: { type: 'object' },
    cliCommand: { name: 'help', aliases: ['?'], examples: ['help'] },
    ui: { component: 'help-panel', position: 'sidebar', order: 0 },
    mcpToolName: 'help',
    apiEndpoint: { method: 'GET', path: '/api/help' },
    surfaces: ['cli', 'ui', 'api', 'mcp'],
  },
  async (input, capCtx) => {
    /* registry.list() -> group by category, include cliCommand name + aliases */
  },
)
```

## Store Contract
- Uses `registry` (closure arg of `registerCommandParityCapabilities`) — `registry.list(): UnifiedCapability[]`.
- No DB writes.

## Test Contract
- Unit: `tests/unit/engines/command-parity-capabilities.test.ts`
  - calling `cap:help` returns a categorized list; every entry that declares `cliCommand` exposes `name`.
  - response includes the capability's own id (`cap:help`).
- The catalog pattern `help` now resolves (no dangling).
