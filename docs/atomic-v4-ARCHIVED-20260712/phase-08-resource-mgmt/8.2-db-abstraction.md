# Unit 8.2 — Database Abstraction Layer: Multi-Strategy Store

**Phase:** 8 | **ID:** 8.2 | **Dependencies:** 7.6

## Problem

All store implementations are hardcoded to Prisma + SQLite. For production scale (100+ concurrent users, high write throughput), SQLite's single-writer limitation becomes a bottleneck. The system should be able to switch to PostgreSQL or other databases via configuration.

## Re-Programmable Design

A **DbStrategyPolicy** selects the database backend and configures connection:

```typescript
interface DbStrategyPolicy {
  backend: 'sqlite' | 'postgres' | 'mysql'
  connectionString: string
  poolSize: number                // connection pool size
  poolTimeoutMs: number
  sslMode: 'disable' | 'prefer' | 'require'
  migrations: 'auto' | 'manual'
  readReplicaUrl?: string         // optional read replica for scaling reads
}
```

### Architecture: Store Interface + Strategy Pattern

```
                    ┌─────────────────┐
                    │  Store Contract │  (interface — already exists)
                    │  e.g. ConvStore │
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              │              │              │
    ┌─────────▼──┐  ┌────────▼───┐  ┌──────▼────┐
    │ SQLiteImpl │  │ PGImpl     │  │ CustomImpl│
    │ (current)  │  │ (future)   │  │ (plugin)  │
    └────────────┘  └────────────┘  └───────────┘
```

### Implementation: Store Factory

```typescript
// New file: src/storage/store-factory.ts

import type { CapStoreDb } from './db.js'

export type StoreBackend = 'sqlite' | 'postgres' | 'mysql'

export interface StoreFactoryOptions {
  backend: StoreBackend
  db: CapStoreDb
  policyStore: PolicyStore
}

export class StoreFactory {
  private backend: StoreBackend

  constructor(private opts: StoreFactoryOptions) {
    this.backend = opts.backend
  }

  createConversationStore(): ConversationStore {
    switch (this.backend) {
      case 'sqlite':
        return new ConversationStoreImpl(this.opts.db)
      case 'postgres':
        return new ConversationStorePgImpl(this.opts.db)
      default:
        return new ConversationStoreImpl(this.opts.db) // fallback
    }
  }

  createGovernorStore(): GovernorStore {
    switch (this.backend) {
      case 'sqlite':
        return new GovernorStoreImpl(this.opts.db)
      case 'postgres':
        return new GovernorStorePgImpl(this.opts.db)
      default:
        return new GovernorStoreImpl(this.opts.db)
    }
  }

  // ... one method per store contract
}
```

### Prisma Multi-Database Support

Prisma already supports multiple databases via the `datasource` block in `schema.prisma`. The key is making the connection string configurable:

```prisma
// prisma/schema.prisma
datasource db {
  provider = sqlite  // or postgresql or mysql
  url      = env("DATABASE_URL")
}
```

The `DATABASE_URL` environment variable (or DB strategy policy) determines which database is used. Prisma generates different client code per provider, so we need to:

1. Use `prisma generate` with the correct provider
2. OR use a schema-based approach where the same TS interfaces work across databases

### Important: Don't Over-Engineer

For v4, the practical path is:
1. Keep SQLite as default (works for single-user/local-first)
2. Document the migration path to PostgreSQL
3. Ensure all stores use the interface pattern (already done)
4. Add a `DATABASE_URL` configuration that switches Prisma's connection
5. PostgreSQL store implementations can be added incrementally

The store interface pattern means PostgreSQL implementations can be added one at a time — not a big-bang rewrite.
