## Root Cause Analysis

The current Tauri V2 Windows build produces an NSIS installer that installs files to disk, but when the user launches the app, **nothing visible happens**. This is caused by **five compounding bugs** that must all be fixed together:

### Bug 1: Broken Frontend (Critical — Blank Window)

**File:** `scripts/tauri/prepare-frontend.ts`

The script builds Next.js with `output: "standalone"` (Node.js server mode), then manually copies `.next/static/` to `frontend/out/` and generates a minimal `index.html` with raw `<script>` tags from `build-manifest.json`. This produces a **completely broken frontend** because:

- `output: "standalone"` generates a Node.js server + minimal `.next/static`. It does NOT produce a static site with working HTML pages.
- The manually created `index.html` only has polyfill/root script tags. It lacks the Next.js router bootstrap, page chunks, React runtime, and data hydration scripts.
- The result: Tauri's WebView loads `index.html` and renders a blank white page with `<div id="__next"></div>` and nothing else.

**Fix:** Switch to `output: "export"` which produces a complete static site. Remove the manual HTML generation entirely.

### Bug 2: Hardcoded Windows Path in next.config.mjs

**File:** `frontend/next.config.mjs`

```js
turbopack: {
  root: "C:\\0-BlackBoxProject-0\\vivim-final\\frontend",  // DEVELOPER-SPECIFIC
}
```

This causes build failures on any machine except the original developer's. The `prepare-frontend.ts` fix above also strips this.

**Fix:** Remove the `turbopack` block entirely and set `output: "export"`.

### Bug 3: Window Shown Before Backend Ready (UX Bug)

**File:** `src-tauri/tauri.conf.json`

```json
"visible": true  // Window shows immediately
```

Combined with `src-tauri/src/lib.rs` which has no mechanism to wait for the backend sidecar to start before showing the window, the user sees a blank window (from Bug 1) immediately. Even after Bug 1 is fixed, the window would show an error page while the backend boots (~8 seconds).

**Fix:** Set `visible: false` in tauri.conf.json. In `lib.rs`, listen for the `backend-ready` event and only call `window.show()` + `window.set_focus()` after the backend signals it's listening.

### Bug 4: WIX Target + Updater Placeholders (Build Failure)

**File:** `src-tauri/tauri.conf.json`

```json
"targets": ["msi", "nsis"],  // msi = WIX
"createUpdaterArtifacts": true,
"pubkey": "REPLACE_WITH_TAURI_SIGNING_PUBKEY"  // Placeholder!
```

- `"msi"` target requires WIX toolset which may not be installed, causing build failure.
- `createUpdaterArtifacts: true` with a placeholder pubkey causes the build to attempt code signing and fail.

**Fix:** Remove `"msi"` from targets (NSIS only). Set `createUpdaterArtifacts: false`. Remove the `plugins.updater` block.

### Bug 5: Port Mismatch / Launch Confusion

**Files:** `src-tauri/src/lib.rs`, `scripts/tauri/launch.bat`

- `lib.rs` defaults to port **9421**
- `launch.bat` hardcodes port **9420**
- The old custom NSIS installer (`installer.nsi`) launches `launch.bat` which opens a **browser** — not the Tauri window

This is redundant and confusing. The Tauri app manages its own window; `launch.bat` and the custom `installer.nsi` are vestiges of a pre-Tauri approach.

**Fix:** Use Tauri's built-in NSIS installer (generated by `cargo tauri build --bundles nsis`). Remove the custom `installer.nsi`, `launch.bat`, and `build-installer.ps1`. The sidecar always uses port 9421 (or next available via `findAvailablePort` in `sidecar-entry.ts`).

## Technical Details

### Why `output: "export"` Instead of `output: "standalone"`

Tauri loads frontend files from disk via its own custom protocol (`tauri://localhost`). It does NOT run a Node.js server. Therefore the frontend must be a **static site** — plain HTML, JS, and CSS files.

- `output: "standalone"` → Produces a Node.js server + minimal static files. **WRONG for Tauri.**
- `output: "export"` → Produces a complete static site. **CORRECT for Tauri.**

### Why the Window Starts Hidden

The Bun sidecar takes ~5-10 seconds to compile its engines and start listening. If the window is visible immediately, the user sees a blank page or error during this time. By starting hidden and showing on `backend-ready`, the user only sees the window when the backend is actually serving.

### Why NSIS Only (No WIX)

- WIX requires a separate toolset installation and generates MSI files which are larger
- NSIS produces smaller, faster installers and is the standard for Tauri V2 Windows apps
- The user explicitly requested no WIX

### CSP Changes

Added `'unsafe-eval'` and `'unsafe-inline'` to `script-src`, and `http://localhost:*` to `connect-src`. The static export may include inline scripts from Next.js, and the backend may bind to `localhost` (in addition to `127.0.0.1`). These are necessary for the Tauri WebView to function correctly.
