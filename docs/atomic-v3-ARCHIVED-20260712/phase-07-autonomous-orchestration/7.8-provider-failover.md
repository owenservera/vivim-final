# Unit 7.8 — Provider failover mid-task

**Source:** v3 Overview §1.4; `docs/master-plan-v3/PHASE-07-autonomous-orchestration.md` §7.8
**Design Doc:** `docs/master-plan-v3/PHASE-07-autonomous-orchestration.md` §7.8
**Depends on:** 5.5
**Produces:** On step failure, agent can reroute to a backup provider.

---

## Context

If a provider fails mid-task (e.g. Ollama crashes, or a cloud LLM 429s), the agent should not just die — it should (a) consult `routing_preference` for fallback providers, (b) emit a HITL gate "Step failed on {provider}, retry on {fallback}?", and (c) on approval, re-execute the step against the fallback with adapted input (different selectors/endpoints). Builds on `ProviderRouter` routing (5.5).

## Existing Baseline

- `src/engines/autonomous-execution.ts:636` — `healSelector` is the step-failure path; we add provider-failover before/around selector healing.
- `src/engines/provider-mux.ts` — `MuxDispatcher` / `ProviderRouter` with `routing_preference` (5.5). Provides `fallbacksFor(providerId)`.
- `src/engines/provider-registrar.ts` (5.1) — registry of providers (id, type, isLocal).
- `docs/atomic-v3/phase-07-autonomous-orchestration/7.3-hitl-clarify.md` — `clarify` / gate emit reused for the approval.

## Interface

### New method on `AutonomousExecutionEngine`

```typescript
export class AutonomousExecutionEngine {
  // ...
  private async executeStepWithFailover(step: AutonomousStep, task: AutonomousTask): Promise<StepResult> {
    try {
      return await this.executeStep(step, task)
    } catch (err) {
      const failedProvider = this.currentProvider(task)
      const fallback = this.router.fallbacksFor(failedProvider)
      if (fallback.length === 0) throw err
      const choice = await this.clarify(
        step,
        `Step failed on ${failedProvider}. Retry on ${fallback[0]}?`,
        'option',
        { options: fallback },
      )
      return this.executeStepAgainst(step, choice, this.adaptInput(step, choice))
    }
  }
}
```

### `ProviderRouter` extension (5.5)

```typescript
// src/engines/provider-mux.ts
fallbacksFor(providerId: string): string[] {
  return this.preferences.get(providerId)?.fallbacks ?? []
}
```

## Acceptance Criteria

1. Step failure consults `routing_preference` for fallback providers (via `ProviderRouter.fallbacksFor`).
2. When a fallback exists, an `agent:clarify` `option` gate is emitted offering the fallback(s).
3. On approval, the step is re-executed against the chosen fallback with adapted input.
4. No fallback configured → original error propagates (no hang).
5. `bun run devops gate` passes.

## Tests

`tests/unit/engines/autonomous-failover.test.ts` (mock router + clarify):
- failure with fallback → `clarify` emitted with `options:[fallback]`; approval → re-execute against fallback.
- failure with no fallback → error thrown, no gate emitted.
- approval path re-executes with adapted input.
