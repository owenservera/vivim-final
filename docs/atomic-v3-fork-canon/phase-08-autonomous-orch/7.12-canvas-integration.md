# Unit 7.12 — Autonomous integration with canvases

**Source:** v3 Overview §1.6, §1.8; `docs/master-plan-v3/PHASE-07-autonomous-orchestration.md` §7.12
**Design Doc:** `docs/master-plan-v3/PHASE-07-autonomous-orchestration.md` §7.12
**Depends on:** Phase 3
**Produces:** Tasks can spawn canvases + operate on them (`canvas_spawn` / `canvas_mutate`).

---

## Context

A real autonomous job is "build me a dashboard" — which means the agent must create a canvas and then act on it. This unit wires `AutonomousExecutionEngine` to Phase 3's canvas system: a plan step `action: "canvas_spawn"` creates a canvas (via `CanvasSpawner`); subsequent steps `action: "canvas_mutate"` run on it. This is the end-to-end Scenario A from the overview.

## Existing Baseline

- `src/engines/autonomous-execution.ts` — `executeStep` / `runStep` (7.9) is where action dispatch happens. We add `canvas_spawn` / `canvas_mutate` handling.
- `docs/atomic-v3/phase-03-html-canvas/3.3-canvas-spawner.md` — `CanvasSpawner.spawn(opts)` returns `{ canvasId, tabId, url }` and is the basis for spawning.
- `docs/atomic-v3/phase-03-html-canvas/3.x` — `CanvasExecutor` runs JS in a canvas; `canvas_mutate` maps to `executor.run(canvasId, js)`.
- `src/engines/unified-registry.ts` (1.3) — canvas capabilities registered so the planner (7.1) can emit `canvas_spawn` as a step.
- `docs/atomic-v3/phase-07-autonomous-orchestration/7.9-composite-step.md` — the step-tree records canvas actions as sub-steps.

## Interface

### Change in `src/engines/autonomous-execution.ts`

```typescript
import { CanvasSpawner } from './canvas/canvas-spawner.js'
import { CanvasExecutor } from './canvas/canvas-executor.js'

export class AutonomousExecutionEngine {
  private canvasByTask = new Map<string, string>() // taskId -> canvasId

  private async runStep(step: AutonomousStep, task: AutonomousTask): Promise<void> {
    if (step.action === 'canvas_spawn') {
      const c = await this.spawner.spawn({ title: step.actionInput.title as string ?? task.goal.description })
      this.canvasByTask.set(task.id, c.canvasId)
      step.status = 'completed'
      this.provenance.recordEdge(step.id, c.canvasId, 'canvas-spawn', {})
      return
    }
    if (step.action === 'canvas_mutate') {
      const canvasId = this.canvasByTask.get(task.id)
      if (!canvasId) throw new CapStoreError('canvas_mutate with no spawned canvas')
      await this.executor.run(canvasId, String(step.actionInput.js))
      step.status = 'completed'
      return
    }
    await this.executeStepWithHealing(step, task) // existing path
  }
}
```

registerCapability({ id: 'cap:canvas:spawn', slug: 'canvas_spawn', name: 'Spawn Canvas', ... })

## Acceptance Criteria

1. A step `action: 'canvas_spawn'` creates a canvas via `CanvasSpawner.spawn` and records its `canvasId` for the task.
2. A later `action: 'canvas_mutate'` runs JS against that task's canvas (no canvas → throws).
3. Both are recorded as sub-steps in the task tree (provenance `canvas-spawn` edge).
4. `canvas_spawn` / `canvas_mutate` are resolvable plan steps (registered capabilities), so the planner (7.1) can emit them.
5. End-to-end: "build me a dashboard" spawns a canvas and mutates it across multiple steps.
6. `bun run devops gate` passes.

## Tests

`tests/unit/engines/autonomous-canvas.test.ts` (mock `CanvasSpawner` + `CanvasExecutor`):
- `canvas_spawn` → `spawner.spawn` called; task canvasId stored.
- `canvas_mutate` after spawn → `executor.run(canvasId, js)` called.
- `canvas_mutate` with no canvas → throws `CapStoreError`.
