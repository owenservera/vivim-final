# Dual-DB Architecture: Complete System Reference

**Version:** 1.0 (2026-08-14)
**Status:** Implemented (Steps 1-6, 8-10); Step 7 (seed split) pending

---

## 1. Architecture Overview

The 200-model Prisma schema has been physically split into two SQLite databases:

| Database | Purpose | Models | Client |
|----------|---------|--------|--------|
| `prisma/data/system.db` | Providers, capabilities, routing, telemetry, health, config, harness, MCP, workflows, kernels, discovery, UI system, ops, agent definitions, AI gateway | 111 | `SystemPrismaClient` |
| `prisma/data/user.db` | Conversations, nodes, memory, sessions, collections, entities, workspaces, sync, context, autonomous agents, mux, webapp, platform extensions, topics | 90 | `UserPrismaClient` |

Both databases include a `SchemaMeta` table for version tracking.

### Why Split?

1. **Backup isolation** — system DB (release-pinned) vs user DB (session-pinned)
2. **Migration independence** — schema changes to providers don't touch conversation data
3. **Future multi-tenant** — user DB can be per-user while system DB is shared
4. **Boundary enforcement** — compile-time + runtime guarantees no cross-DB `@relation`

## 2. Schema Layout

### Original (preserved for reference)

```
prisma/schema.prisma          # 200 models, 3957 LOC (legacy, do not edit)
```

### New split layout

```
prisma/
  system/
    schema.prisma              # Generator + datasource + 111 models (composed single-file)
  user/
    schema.prisma              # Generator + datasource + 90 models (composed single-file)
  data/
    system.db                  # Runtime SQLite (created on first boot)
    user.db                    # Runtime SQLite (created on first boot)
```

### Schema generation

Schemas are generated by `scripts/split-schema.ts`:

```bash
bun run scripts/split-schema.ts
```

This reads `prisma/schema.prisma`, classifies each model by its `// ctx:` tag, strips cross-boundary `@relation` fields, and writes composed single-file schemas to `prisma/system/schema.prisma` and `prisma/user/schema.prisma`.

**Do NOT use `prismaSchemaFolder`** — Prisma 6.19's folder preview feature does not generate model types in the output client. Single-file schemas are required.

## 5. Client Wiring (`src/storage/prisma.ts`)

### Singletons

| Function | Returns | DB |
|----------|---------|-----|
| `getSystemPrisma()` | `SystemPrismaClient` | system.db |
| `getUserPrisma()` | `UserPrismaClient` | user.db |
| `getPrisma()` | `SystemPrismaClient` | system.db (deprecated shim) |
| `closePrisma()` | `Promise<void>` | disconnects both |

### URL resolution

1. Check env: `SYSTEM_DATABASE_URL` / `USER_DATABASE_URL`
2. Fallback to config: `config.systemDbPath` / `config.userDbPath`
3. Resolve relative `file:.` paths against `prisma/system/` or `prisma/user/`
4. Auto-create parent directory if missing

### WAL mode

```ts
import { initPrismaWal } from '../storage/prisma.js'
await initPrismaWal(client)  // runs PRAGMA journal_mode=WAL
```

## 6. CapStoreDb (`src/storage/db.ts`)

The `CapStoreDb` class holds both clients:

```ts
class CapStoreDb {
  readonly systemPrisma: SystemPrismaClient  // system-side tables
  readonly userPrisma: UserPrismaClient      // user-side tables
  readonly prisma: FullPrismaClient          // DEPRECATED backward-compat shim
}
```

### Usage pattern for store impls

```ts
// System-side store (providers, capabilities, etc.)
class ProviderStoreImpl {
  constructor(db: CapStoreDb) {
    this.prisma = db.systemPrisma  // ✅ typed to system client
  }
}

// User-side store (conversations, nodes, etc.)
class ConversationStoreImpl {
  constructor(db: CapStoreDb) {
    this.prisma = db.userPrisma  // ✅ typed to user client
  }
}

// LEGACY — still works but deprecated
class SomeStoreImpl {
  constructor(db: CapStoreDb) {
    this.prisma = db.prisma  // ⚠️ FullPrismaClient, use typed clients instead
  }
}
```

## 7. Cross-Boundary Rules

### The Rule

> **No `@relation` may cross the system/user boundary.** Cross-DB references use plain `String` columns.

### Current state

All cross-boundary references are already plain `String` columns (no `@relation`). The split-schema script strips any that appear during schema generation.

### Soft-ref convention

When a user-side model references a system-side model by ID:

```prisma
// In user schema:
model Conversation {
  providerId String  // soft-ref: system.ProviderDefinition.id
  // ... no @relation to ProviderDefinition
}
```

### Enforcement

The arch test `tests/arch/dual-db-boundary.test.ts` scans both schemas and fails if any `@relation` crosses the boundary. Runs as part of `bun run test:arch` and CI.

## 8. SchemaMeta Versioning

Both databases carry a `SchemaMeta` table:

```prisma
model SchemaMeta {
  key   String
  value String
  @@id([key, value])
}
```

### Required keys

| Key | Example | Purpose |
|-----|---------|---------|
| `schema_version` | `"2026.08.14-014"` | Semantic version of the DB schema |
| `migration_checksum` | sha256 of migrations dir | Detects hand-edited migrations |
| `min_compatible_seed_version` | `"2026.08.10"` | Oldest seed bundle this schema accepts |
| `min_compatible_app_version` | `"1.3.14"` | Oldest app build allowed to open this DB |

### Boot check (`src/storage/verify-compat.ts`)

Before any engine touches DB data, the boot pipeline runs:

```ts
await verifySchemaCompat(getSystemPrisma(), 'system')
await verifySchemaCompat(getUserPrisma(), 'user')
```

This validates:
- `schema_version` exists (DB predates versioning → hard error)
- `min_compatible_app_version` is satisfied (app too old → hard error)
- `SchemaMeta` table missing → warn (DB may be uninitialized)

## 9. Boot Sequence

```
orchestrateBootstrap(port)
  └─ bootstrapSeedsPhase(ctx)
       ├─ getDb() → CapStoreDb (both clients initialized)
       ├─ verifySchemaCompat(systemPrisma, 'system')  ← NEW
       ├─ verifySchemaCompat(userPrisma, 'user')      ← NEW
       ├─ applyPendingMigrations()
       ├─ if needsSeed:
       │    ├─ snapshot restore (seed-snapshot.db → dbPath)
       │    └─ runIndividualSeeds(db, registrar, providerStore, log)
       └─ providerRegistry.initialize()
  └─ bootstrapStoresPhase(ctx)
  └─ bootstrapKnowledgePhase(ctx)
  └─ bootstrapCapabilitiesPhase(ctx)
  └─ bootstrapLifecyclePhase(ctx)
```

```bash
# Development (creates migration + applies)
bun run prisma:migrate:dev:system
bun run prisma:migrate:dev:user

bun run prisma:migrate:prod:system

```

### Studio

```bash
bun run prisma:studio:system    # opens Studio for system.db
bun run prisma:studio:user      # opens Studio for user.db
```

### CI drift detection

```bash
# In scripts/ci.ts — runs automatically
prisma migrate diff --from-migrations prisma/system/migrations --to-schema-datamodel prisma/system/schema.prisma --exit-code
prisma migrate diff --from-migrations prisma/user/migrations --to-schema-datamodel prisma/user/schema.prisma --exit-code
```

Fails if schema has unmigrated changes.

## 11. Backup & Restore

### Paired snapshots

```bash
bun run db:backup     # creates snapshots/<timestamp>/{system.db,user.db,snapshot.json}
bun run db:restore    # restores from latest snapshot
bun run db:restore --from <timestamp>  # restores from specific snapshot
```

### Snapshot format

```
snapshots/
  2026-08-14T09-00Z/
    system.db
    user.db
    system-meta.json    # SchemaMeta rows from system.db
    user-meta.json      # SchemaMeta rows from user.db
    snapshot.json       # { timestamp, app_version, system_schema_version, user_schema_version }
```

### db-doctor

```bash
bun run db:doctor     # scans all .db files, classifies system/user, checks SchemaMeta
```

Reports: schema match, version, migration compatibility, orphaned files.

## 13. Adding a New Model

### To system DB

1. Add model to `prisma/schema.prisma` with `// ctx: <system-context>`
2. Run `bun run scripts/split-schema.ts`
3. Run `bunx prisma migrate dev --schema=prisma/system/schema.prisma`
4. Run `bun run prisma:generate:system`

### To user DB

1. Add model to `prisma/schema.prisma` with `// ctx: <user-context>`
2. Run `bun run scripts/split-schema.ts`
3. Run `bunx prisma migrate dev --schema=prisma/user/schema.prisma`
4. Run `bun run prisma:generate:user`

### Context assignment

Choose the context that best fits the model's bounded context. See Section 3 for the full list. If unsure, check where the model's data is read/written — system-side stores use `db.systemPrisma`, user-side stores use `db.userPrisma`.

## 14. Known Limitations

1. **Backward-compat shim** — `db.prisma` casts `systemPrisma` to `FullPrismaClient`. Store impls using `db.prisma` for user-side tables will silently read from system DB. Migration to typed clients is ongoing.

2. **Seed infrastructure** — 3 seeds write user-side data via system shim (automation, memory-intelligence, seed-taxonomy). Step 7 will fix this.

3. **Standalone scripts** — `command-descriptions/seed.ts` and `capabilities/seed-taxonomy.ts` create own `PrismaClient` from `@prisma/client`. They'll need updating after the split.

4. **Snapshot restore** — Current snapshot is single-file (`seed-snapshot.db`). Needs rewrite for paired snapshots.

5. **No cross-DB joins** — Queries that need data from both DBs must make two separate queries and join in application code.

## 15. Migration Guide (for existing code)

### Before (single client)

```ts
import { PrismaClient } from '@prisma/client'
const prisma = new PrismaClient()
await prisma.providerDefinition.findMany()
await prisma.conversation.findMany()
```

### After (dual clients)

```ts
import { getSystemPrisma, getUserPrisma } from '../storage/prisma.js'
const systemPrisma = getSystemPrisma()
const userPrisma = getUserPrisma()

await systemPrisma.providerDefinition.findMany()  // system
await userPrisma.conversation.findMany()           // user
```

### Store impl pattern

```ts
// Accept CapStoreDb, use the typed client for your side
class MySystemStore {
  constructor(db: CapStoreDb) {
    this.prisma = db.systemPrisma
  }
}

class MyUserStore {
  constructor(db: CapStoreDb) {
    this.prisma = db.userPrisma
  }
}
```
