# Unit 1.9 — Iterative ledger-driven loop (improve → test → debug → improve)

**Source:** PRD R5, R8; the user's core ask — "step-by-step improve, real-world test, debug, improve…
giving the LLM flexibility but keeping it on-task and making progress."
**Depends on:** 1.1 (catalog/goal-gate), 1.5 (goal-gate), 1.4 (process-guard), 1.6 (guard)
**Produces:** `loop --objective` / `--resume` / `--reset` — a persisted progress ledger that lets a
flexible LLM drive an iterative dev loop while staying on-task and showing progress.

---

## Context

The prior `loop` was a single discover+engage pass. It could not *iterate*: no memory of what was
tried, no per-cycle real-world test, no progress signal. The LLM would either do everything in one
shot (risky) or lose the thread across cycles. The fix splits roles: **the LLM implements each
proposed step; the loop coordinates + evaluates + records.** A ledger is the single source of truth.

## Interface

### New files
- `devops/runtime-test/loop-state.ts` — `loadLoopState/saveLoopState/initLoopState/clearLoopState`.
- `devops/runtime-test/iterate.ts` — `runIterativeLoop({objective?, resume?, force?})`.

### CLI
- `loop --objective="..."` → init ledger, evaluate (typecheck + backend probe), propose step 1.
- `loop --resume` → evaluate last step, record pass/fail, propose next or conclude (`done`/`blocked`).
- `loop --reset` → clear ledger.

### Ledger (`.runtime/loop-state.json`)
`{objective, maxCycles, cycle, status, history:[{cycle,action,status,checks,result}], nextStep}`.
