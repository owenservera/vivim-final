# Unit 1.5 — Goal-resolution gate in loop

**Source:** PRD R5, R8; Scenario E
**Depends on:** 1.1 (offline catalog)
**Produces:** `loop` halts with `needsClarification` when the goal maps to no capability, instead of
building the wrong thing. Enforces the SKILL's "interview-first" rule as code.

---

## Context

The SKILL says "interview-first" but gives no enforceable stop. An autonomous CLI agent (Kilocode/
OpenCode) often skips the `question` tool and proceeds with an assumption — e.g. building a one-off
"dark mode" component that violates FRONTEND=BACKEND and the "render from `ResolvedCapability`"
rule. The fix is a goal gate: if the goal cannot be reduced to a capability id + slug, the loop
returns `needsClarification` and exits (no spin).

## Interface

### New file: `devops/runtime-test/goal-gate.ts`
- `assessGoal(goal, opts?: { probe?: boolean }): Promise<GoalAssessment>` — matches the offline
  catalog (id/slug/name) first (no server); optionally probes `/api/interpret`. Returns
  `{resolved, capabilityId?, slug?, needsClarification, reason?}`.

### Modified: `devops/index.ts` `loop` case
- Before `runOrchestrationCycle`, run `assessGoal(goal, { probe: true })`; if `needsClarification`
  and `--force` not passed, print `{ok:false, needsClarification, reason, hint}` and exit 1.

## Steps
1. Implement `goal-gate.ts`.
2. Wire the gate into the `loop` case.
3. Document in SKILL.md.

## Acceptance
- `loop --goal="make the app support dark mode"` returns `needsClarification` immediately (no spin).
- `loop --goal="list conversations"` resolves (catalog match) and would proceed.
- `loop --goal="..." --force` bypasses the gate.
- `typecheck` clean.
