# Unit 5.3 — Backend Handler Scaffold (build.ts handler)

**Depends on:** 3.2, 4.3
**Produces:** `devops/runtime-test/build.ts` (handler generator), `src/engines/*caps.ts`, `src/server/**`
**Source:** `docs/atomic-runtime/RUNTIME-OS-DESIGN.md` §3.8

## Problem
When `discover-backend` (3.2) finds a provider capability lacking a handler/intent (or a new provider
capability the agent wants to add), the loop must scaffold a `UnifiedCapability` handler + register it
with `surfaces: ['cli','ui','api']` + add NL patterns (1.4) — proving it can build backend systems.

## Approach
- `build.ts generateHandler(provider, cap)`: create a capability via `makeCapability`/`registerSessionCaps`
  pattern in the right `*caps.ts`, register NL patterns in `catalog.ts` (1.4), and (if 1.3) write a
  `capability_taxonomy` row via `registerCapability`.
- Re-run `test` (4.1) + `discover-backend` to confirm the new cap is live and addressable.
- Keep Governor Canon + Store Contracts (engine depends on `storage/contracts`, never `impl`).

## Acceptance
- Generated handler appears in `GET /api/capabilities` and is executable end-to-end.
- NL pattern resolves to the new capability (1.4).
- `bunx tsc --noEmit` + `bun run lint` clean.

## Tests
- `tests/integration/runtime-test/build-handler.test.ts`: generate → live execute green.
