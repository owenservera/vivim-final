# ADR-015: ChromeGovernor Admission Control & Crash Recovery

**Status:** APPROVED
**Date:** 2026-07-19
**Author:** research-loop
**Reviewers:** None yet
**Related Units:** chrome-fleet-management-sota-2026 (research), fleet-supervisor
**Related Docs:** `docs/research/chrome-fleet-graceful-plan.md`, `docs/research/code-paths/chrome-fleet-management-path.md`

## Problem Statement

vivim-final's Chrome fleet is SOTA-aligned on the big patterns (single orchestrator via
`ChromeGovernor`, persistent `chrome-profiles/`, one-Chrome-per-provider). However
`FleetSupervisor.spawn` has **no admission control**: it does not bound concurrent launches,
does not queue overflow, does not check host pressure before spending a Chrome, and retries
launch failure **zero times** (the initial `spawn` body at fleet-supervisor.ts:216-257 tries
`launchChrome` once and falls through to `status:'error'`). Runtime crash recovery exists
(`autoRestart`/`maxRestarts`/`ensureRunning`), but launch-time failure does not.

Research (`chrome-fleet-management-sota-2026`, 14 sources, confidence High) shows the SOTA
primitives are: bounded `Limiter` (browserless), pre-spawn pressure cascade, and first-class
retry-on-crash (`puppeteer-cluster` retryLimit/retryDelay). We adopt these inside the governor.

## Context

- `FleetSupervisor.spawn` (fleet-supervisor.ts:182) is the real spawn entry; `ChromeGovernor.spawn`
  (chrome-governor.ts:777) delegates to it. This is the correct seam.
- `FleetSupervisorOptions` (fleet-supervisor.ts:35) is the live config bag, built from `FleetConfig`
  (chrome-governor.ts:750). New fields must be added to **both** so they flow through.
- `FleetInstance` already carries `consecutiveFailures`; `ensureRunning` already uses it with a
  circuit breaker. Retry-on-crash must **compose** with this, not fork it.
- `PortReaper` (port-reaper.ts) already tracks PIDs; `killExistingChromeForProfile` does
  best-effort kill. Windows child-Chrome reaping on shutdown is the remaining gap.
- **Governor Canon invariant:** only `ChromeGovernor` (via `FleetSupervisor`/`launchChrome`) touches
  CDP. The limiter and pressure gate contain **zero CDP**.

## Options Considered

### Option A: Governor-owned Limiter + Pressure Gate + Retry (SELECTED)

Add `FleetLimiter` (new `fleet-limiter.ts`), `readSystemPressure` (new `system-pressure.ts`), and a
bounded retry loop inside `spawn`. All additive optional config; default-disabled.

**Pros:** Preserves Governor Canon; no new transport; no new dependency; proven OSS shapes;
composes with existing circuit breaker.
**Cons:** Must thread options through the one `FleetSupervisor` constructor; small test surface to add.
**Effort:** M **Risk:** low

### Option B: Adopt puppeteer-cluster wholesale

**Pros:** Batteries-included.
**Cons:** Second CDP surface → violates Governor Canon; vivim uses raw CDP, not Puppeteer; heavy.
**Effort:** L **Risk:** high

### Option C: Run browserless as a sidecar

**Pros:** Battle-tested fleet manager.
**Cons:** Docker/remote CDP breaks local-first + per-provider profile model; overkill.
**Effort:** L **Risk:** medium

### Option D: Limiter as a separate engine calling the governor

**Pros:** Isolated module.
**Cons:** Creates a lifecycle owner outside the governor → violates Governor Canon; limiter must
gate the single spawn path, so it belongs inside `FleetSupervisor`.
**Effort:** M **Risk:** medium

## Decision

**Selected Option:** A — governor-owned admission control + crash recovery.

**Rationale:** It is the only option that satisfies the Governor Canon while closing all four
research gaps with proven, dependency-free primitives. It is additive (default-off) so blast
radius is minimal.

## Consequences

### Positive
- Bounded concurrency prevents Chrome over-launch storms during provider bursts.
- Pressure gate refuses/defers spawns on saturated hosts instead of OOMing.
- Launch failures get bounded exponential-backoff retries (distinct from runtime `autoRestart`).
- Windows orphan Chrome trees are reaped on shutdown (no leaked PIDs).
- Every rejection/queue/timeout/retry emits a `FleetEvent` → observable fleet health.

### Negative / Trade-offs
- New optional config surface to maintain (`FleetConfig` + `FleetSupervisorOptions`).
- Callers must handle three new typed errors (`FleetQueueFullError`, `FleetQueueTimeoutError`,
  `FleetPressureOverloadError`); existing callers already `await` spawn and can let them propagate.
- `queueTimeoutMs` must be tuned so callers fail fast rather than hang (default 30s).

### Neutral
- `spawnRetryLimit` defaults to 0 → current single-attempt behavior preserved until opted in.

## Implementation Notes (see chrome-fleet-graceful-plan.md)

- New `FleetLimiter` class: `acquire`/`release`/`stats`; overflow → `FleetQueueFullError`;
  timeout → `FleetQueueTimeoutError`.
- New `readSystemPressure()`: Node `os.loadavg`/`freemem`/`totalmem`, no deps.
- `spawn()` wraps `launchChrome` in `for attempt <= spawnRetryLimit` with exp backoff; reuses
  `consecutiveFailures`.
- Windows reaper: `portReaper.reapTree(pid)` + `beforeExit`/`SIGTERM`/`SIGINT` → `killAll()`
  (idempotent guard).
- New `FleetEvent` types: `queue_full`, `queue_timeout`, `spawn_rejected_pressure`, `spawn_retry`.
- Tests: limiter unit, pressure gate, retry, reaper (Windows-fenced), integration drain.
