# ADR-016: Tauri v2 Desktop Product Strategy (Bun Sidecar Architecture)

**Status:** APPROVED
**Date:** 2026-07-19
**Author:** kilo
**Reviewers:** None yet
**Related Units:** 026-tauri-desktop-mvp, spec 015

## Problem Statement

vivim-final is a mature local-first TS engine platform (13 engines, Bun + Prisma) but is
only runnable via `bun run serve` + a browser. We need a production, installable Windows
product strategy now — future-proof and low-rewrite-risk — while still in active development.

## Context

- Backend: `src/server/index.ts` (`createServerWithEngines`) on Bun, REST + WS, local-first.
- Frontend: `web/ui` React 19 + Vite + Zustand, already talks to the backend via `api/client.ts`
  (supports `VITE_API_URL`, already proxies `/api` and `/ws`).
- Toolchain present: Node 24, Bun 1.3.14, Rust 1.95 + Cargo. **Bun compiles TS→native `.exe`
  verified working (~2s, runs on win32).**
- Reference Tauri v2 template available at `.clones/hermes-agent/.../src-tauri`.
- Existing devops invariants flag `process.env` config reads and a low truth score, but those
  are backend-hygiene items, not blockers for the desktop shell.

## Options Considered

### Option A: Full Rust rewrite of the backend
**Pros:** Single binary, max performance. **Cons:** Abandons the entire TS engine layer;
enormous rewrite; kills velocity; violates "we are still in development" constraint.

### Option B: Electron
**Pros:** Familiar. **Cons:** 100MB+ runtime, Chromium bloat, poor security posture; contradicts
the project's local-first/minimal-footprint ethos.

### Option C: Tauri v2 + Bun backend as a sidecar (SELECTED)
Rust core owns only OS-level concerns (window lifecycle, process supervision, signing surface,
updater). The existing Bun backend is shipped as a Tauri sidecar on `127.0.0.1:9421`.
The existing `web/ui` SPA is the WebView frontend.

**Packaging sub-decision (validated 2026-07-19):** compile the backend to a **single standalone
`.exe` via `bun build --compile`** and spawn it as the Tauri sidecar on `127.0.0.1:9421`.
See "Packaging" below — verified end-to-end: the compiled exe boots the full 13-engine stack
(kernel, NLCL, CDP, canvas) and passes the desktop smoke test (`/health`, `/readyz`,
`/api/nlcl/help`) in ~8s. The two gotchas that were resolved:
1. `DATABASE_URL` MUST be absolute (machine-stable app-data path) — a relative `file:./dev.db`
   causes Prisma `Error code 14` inside the standalone runtime. `sidecar-entry.ts` resolves this
   automatically (`%APPDATA%/vivim/app.db` on Windows, etc.).
2. `NODE_ENV=production` disables pino-pretty's worker thread (which can't load under standalone
   compile). Already forced in `sidecar-entry.ts`.

**Pros:** Reuses 100% of TS engines; native speed (~10ms sidecar start, ~50MB); no runtime to
install on user machines; minimal Rust; full-stack TypeScript; Tauri's MSI/NSIS/updater story is
production-grade; honors the One-Entry-Point invariant (Rust is just a host).
**Cons:** Two processes; must supervise sidecar lifecycle (mitigated by Rust supervisor + CSP).

## Decision

**Selected Option:** C — Tauri v2 desktop shell with the Bun backend compiled as a sidecar.

**Rationale:** Future-proof and low-risk. The engine layer is untouched; the desktop shell is an
additive thin host. When the backend later needs a capability the WebView can't provide, it is
added behind the existing UnifiedCapability transport, not a new architecture.

## Packaging (validated 2026-07-19)

**Finding:** `bun build --compile` produces a working native exe that boots the full 13-engine
stack and passes the desktop smoke test in ~8s — **provided `DATABASE_URL` is absolute**. The
earlier `Error code 14` was caused solely by the relative `file:./dev.db` path; with an absolute
app-data path Prisma works inside the standalone runtime. pino-pretty's worker thread is disabled
via `NODE_ENV=production`.

**Mitigations already applied:**
- `src/desktop/sidecar-entry.ts` forces `NODE_ENV=production` (disables pino-pretty) and resolves
  `DATABASE_URL` to an absolute, machine-stable path (`%APPDATA%/vivim/app.db` on Windows,
  `$XDG_DATA_HOME/vivim` / `~/Library/Application Support/vivim` elsewhere) when it is relative.
- `src/cli/index.ts` `main()` is guarded with `if (import.meta.main)` so importing the module
  (in the compiled/sidecar context) does not auto-run the CLI.
- `scripts/tauri/build-sidecar.ps1` compiles `sidecar-entry.ts` to `vivim-server-<triple>.exe`
  via `bun build --compile` and copies it into `src-tauri/binaries/` (matching the
  `externalBin` entry in `tauri.conf.json`).

**Production startup requirement:** the shipped app must include a **synced Prisma DB**
(`bunx prisma db push` against the app-data path at install, or a pre-seeded `app.db`),
otherwise first boot tries to create/migrate and may hang on the broken migration history
(see P3009 — `migrate deploy` is broken in this repo; `db push` works). This is a release-step,
not a code change.

**Test gate added:** `tests/e2e/tauri-sidecar.test.ts` probes `/health`, `/readyz`, and
`/api/nlcl/help` against a live sidecar on `127.0.0.1:9421`; wire into
`bun run devops verify-cross-surface` and the release pipeline (desktop surface).

## Consequences

- `src-tauri/` added: `Cargo.toml`, `tauri.conf.json`, `capabilities/default.json`, sidecar supervisor.
- `src/desktop/sidecar-entry.ts` boots the existing server on loopback.
- `scripts/tauri/build-sidecar.ps1` + `build.ps1` produce the MSI/NSIS/updater artifacts.
- Production: MSI (WiX, perMachine for GPO) + NSIS `-setup.exe` (perUser default) + Authenticode
  signing + `tauri-plugin-updater` with signed `latest.json`. CI: GitHub Actions matrix.
- Rollback/future-proofing: if Bun sidecar ever becomes a liability, the same Rust core can host
  a Rust or Go backend behind the identical `127.0.0.1:9421` contract — the frontend never changes.
