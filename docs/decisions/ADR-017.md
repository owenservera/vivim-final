# ADR-017: Local Code Indexing as a devops Primitive

**Status:** APPROVED
**Date:** 2026-07-20
**Author:** kilo
**Reviewers:** None yet
**Related Units:** CREATE unit `devops/code-index.ts`; `devops/index.ts` (`code-index` subcommand)
**Research gate:** `docs/research/briefs/local-code-indexing-llm-brief.md` (High confidence, 22 sources) — this is the A5 brief gate; it satisfies the research-first invariant (A6: no implementation without a research brief classification).

## Problem Statement

During vibe-coding sessions, sub-agents and the devops loop spend 60–70% of their input
tokens on **exploration** (grep + read whole files) to locate the code they need to edit.
This is slow, token-expensive, and produces no reusable structure. The platform needs a
cheap, offline, always-available code-discovery surface that returns ranked `path:line`
packets instead of forcing full-file reads.

## Context

- Stack: Bun 1.3.14 + TypeScript; `bun:sqlite` ships **FTS5** with zero runtime deps.
- SOTA (22 sources, High confidence) converges on a single architecture: Tree-sitter AST
  chunking → hybrid retrieval (lexical FTS5/BM25 + optional static embeddings fused via
  RRF) → token-budgeted `path:line` packets → offline SQLite → MCP server.
- `codemogger` proves the Bun/TS pattern works (tree-sitter WASM + Turso FTS+vector).
- Adding a Python/Go runtime dependency to the devops CLI would violate local-first/zero-dep
  ethos and break the offline guarantee.
- Sub-agents in this repo cannot call MCP directly, so a CLI surface is also required.

## Options Considered

### Option A: Vendor an existing tool (Semble / codegraph / codemogger / codebase-index)
**Pros:** Feature-complete, benchmarked (Semble ~98% token savings, ~1.5 ms/query, NDCG@10 0.854).
**Cons:** Cross-language runtime deps (Python/Go/Node); not offline by default; can't be
tuned to our ignore rules / scopes; breaks the "deterministic mechanics live in `devops/`"
principle. Rejected — violates local-first and single-source-of-truth invariants.

### Option B: Pluggable embedder + external vector DB
**Pros:** Best semantic quality.
**Cons:** Introduces a heavy runtime (Transformers.js / ONNX) and a second store; overkill
for v1; would block the offline-by-default guarantee. Deferred to a follow-up unit.

### Option C: Native `devops/code-index.ts` — Bun.sqlite FTS5 + RRF, embedder pluggable (SELECTED)
Ignore-aware structural chunker (def boundaries, brace-matched) → `chunks` table + `chunks_fts`
FTS5 external-content index → per-insert transaction-batched build → optional HTTP embedder
(RRF fusion) → token-budgeted `path:line` packets → stdio MCP server. Keyword-only by default,
semantic opt-in.

**Pros:** Zero runtime deps, fully offline, in-repo, tunable to our ignore/scope rules, ships
both CLI and MCP, matches the convergent SOTA exactly, and reuses `Bun.sqlite` FTS5 that the
platform already depends on (ADR-014 dual-store lineage). Default build across all 6 code roots
completes in ~17s / ~18.9k chunks.
**Cons:** Embeddings require a local model (deferred default → lexical fallback with a one-time
warning); AST precision is structural (brace-matched), not full Tree-sitter (upgrade path
documented). Both are acceptable for v1.

## Decision

**Selected Option:** C — native `devops/code-index.ts` as a first-class devops primitive.

**Rationale:** It is the only option that satisfies local-first + zero-dep + offline-by-default
while matching the research-validated architecture. It is the literal fix for the exploration
tax cited in the brief, and it is exposed on both transports the repo actually uses (CLI for
sub-agents, MCP for the top-level agent).

## Interface (contract)

- `code-index build [path] [--all] [--no-embed] [--no-watch] [--db=PATH]` — index code roots
  (default: code-only roots `src, devops, web, scripts, seeds, prisma`; `--all` for whole repo).
  Watch mode is the **default** during coding sessions; `--no-watch` for one-shot.
- `code-index search <query> [--k=N] [--token-budget=N] [--no-embed]` — hybrid lexical +
  semantic search returning ranked `path:line` chunks within a token budget.
- `code-index stats` — file/chunk counts, root, last update.
- `code-index watch [path]` — keep an existing index fresh (hash-gated incremental updates).
- `code-index mcp [--db=PATH]` — stdio JSON-RPC MCP server exposing `code_index_search` and
  `code_index_stats` for the top-level agent.

Storage: `Bun.sqlite` at `.runtime/code-index.sqlite` (`chunks`, `chunks_fts` FTS5
external-content, `files` hash table, `meta`). Embeddings stored as JSON vectors in
`chunks.embedding`; semantic path uses cosine + RRF(k=60) fusion with lexical bm25. Embedder
interface `{ dims, embed(texts): Promise<number[][]> }`; default resolves to an OpenAI-compatible
HTTP endpoint (`nomic-embed-text` at `localhost:11434/v1` by default) and falls back to lexical
if unreachable (env overrides `CODE_INDEX_EMBEDDER_URL` / `CODE_INDEX_EMBEDDER_MODEL`).

## Consequences

- `devops/code-index.ts` added (chunker, storage, embedder, search, watch, MCP, CLI).
- `devops/index.ts` registers `code-index` (import + dispatch + usage).
- `docs/research/` carries the SOTA report, brief (A5 gate), evidence, and code-path.
- Agents should replace grep+read exploration with `devops code-index search` (or the MCP
  `code_index_search` tool). This is now documented in `AGENTS.md` and the `devops` skill.
- Follow-ups (documented, not in v1): Tree-sitter AST chunking; static `potion-code-16M`/
  `all-MiniLM` embedder plug-in; graph edges (callers/callees/impact).
