# ADR-014: Defer Prisma Schema Split to Post-Alpha

- Status: accepted
- Date: 2026-08-07
- Decision-maker: Session 1 development sprint
- Supersedes: ADR-005-run-2026-08-06-B2 (FIX-B2-1, "196-models-in-one-schema")

## Context

The 2026-08-06 review run flagged `prisma/schema.prisma` (196 models, 3,811 LOC,
single file) as P1 FIX-B2-1: "schema split/consolidation for maintainability."
The proposed approach was to split by bounded context (`node.prisma`,
`provider.prisma`, `user.prisma`, `memory.prisma`, `workflow.prisma`) using
Prisma 6's `prismaSchemaFolder` feature.

After triage in session 1, we assess:

- **Correctness risk: NONE.** The schema is functional, migrations apply cleanly,
  and Prisma client generation works. The finding is purely about long-term
  maintainability and ownership boundaries.
- **Migration risk: HIGH.** Splitting 196 models requires:
  - Verifying every cross-file relation resolves
  - Re-baselining the migration history (current: `0001_init` + `0002_agentic_backbone` + `20260805223404_wp10_upgrade`)
  - Re-running every store implementation's seed/snapshot tests
  - Updating `prisma/migrations.bak/` archival policy
- **Time cost: 2–4 days** of focused work with full test re-verification.
- **Alpha blocker: NO.** The schema is correct; only maintainability suffers.

The other 4 alpha P1s (A1-1, A1-2, B1-1, B1-2) are closed in session 1. The
remaining P1 (this one) does not gate the alpha release because it imposes no
correctness, security, or runtime risk.

## Decision

**Defer FIX-B2-1 to post-alpha.** The Prisma schema split is tracked as the
first post-alpha work item. Until then:

1. `prisma/schema.prisma` remains a single file (196 models, 3,811 LOC).
2. Add a header comment to `prisma/schema.prisma` pointing to this ADR.
3. Update `docs/review-system/SCOPE.md` to flag B2-1 as **post-alpha** (not
   alpha-blocking), with this ADR as the tracking home.
4. Update `docs/ALPHA.md` to mark B2-1 as **DEFERRED** with link to this ADR.

## Consequences

**Positive:**
- Alpha ships on time without a risky multi-day refactor.
- The deferral is explicit and tracked — not silently dropped.
- Future engineers (human or agent) reading the schema see the header comment
  and know where to find the plan.

**Negative / risk:**
- Schema continues to grow in single-file form during alpha bug-fix cycles.
  Mitigation: any new model added during alpha must include a one-line comment
  naming its bounded context (e.g. `// ctx: provider`), so the eventual split
  is mechanical.
- Migration history remains linear (no per-context migration folders).
  Acceptable for alpha scale.

## Follow-up tracked

- **Post-alpha unit B2-1-split**: execute the schema split per the original
  ADR-005-run-2026-08-06-B2 proposed approach.
- **Re-open ADR-005-run-2026-08-06-B2**: mark as superseded by this ADR for
  alpha scope; reopen as the canonical plan when the split work begins.
