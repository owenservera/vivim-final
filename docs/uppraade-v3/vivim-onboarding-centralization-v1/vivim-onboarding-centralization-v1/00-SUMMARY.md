# 00 — Executive Summary

## Problem

A fresh user (clone-and-run, or Windows installer) cannot complete first-run onboarding in vivim-final today. The reasons, in priority order:

1. **`frontend/src/shared/onboarding.ts` does not exist** — but 6 files import from it. OnboardingTour subsystem cannot compile.
2. **All 6 `/api/setup/*` routes are called by the frontend but not exposed as Next.js routes** — every first-run API call 404s. (Backend `setup-router.ts` already implements the logic; it just isn't wired to HTTP.)
3. **`/api/onboarding/analytics` and `/api/onboarding/complete-tour` don't exist** — tour analytics silently dropped.
4. **NSIS `launch.bat` doesn't set `FRONTEND_DIR`** — browser opens `:9420`, gets 404.
5. **Sidecar has no DB bootstrap** — empty SQLite at `%LOCALAPPDATA%\vivim\cap-store\cap-store.sqlite` → `count()` throws P2021.
6. **Snapshot auto-restore is unreachable** — `count()` throws before restore can run; path mismatch even if it didn't.
7. **Two competing first-run UIs mounted at once** (GuidedLanding z=2000 + OnboardingTour z=1100) with no coordination.
8. **`MemoryOnboardingStore` is the only impl** — tour state lost on server restart. No Prisma backing, no `UserOnboarding` model.
9. **`launch.bat` keep-alive loop detaches backend** — closing window leaves `vivim-server.exe` orphan.
10. **`next.config.mjs` has hardcoded Windows path** — breaks on non-Windows.
11. **`.env.example` doesn't match what the code reads** — `DATABASE_URL`, `FRONTEND_DIR`, API keys all referenced but not documented.
12. **Dead code** (`features/onboard-flow.tsx`), orphaned artifacts (`frontend/db/custom.db`, `migrations/001_baseline.sql`).

## Solution

13 tasks, grouped into 4 phases. Each task is independently shippable, but the phases are sequenced so each phase produces a verifiable milestone.

### Phase A — Make it compile (Tasks 01, 03)
Deliverable: `bun run dev` boots without type errors. OnboardingTour renders. `/api/onboarding/analytics` and `/api/onboarding/complete-tour` exist.

### Phase B — Make first-run work in dev (Tasks 02, 11, 12, 09)
Deliverable: a fresh-clone user can `bun install && bun run prisma:generate && bun x prisma db push && bun run dev`, open `:3000`, see GuidedLanding, pick a provider, log in to Chrome, and land in a working conversation. Tour state survives server restart.

### Phase C — Make install work (Tasks 04, 05, 06, 10, 07, 08)
Deliverable: the NSIS installer produces a working app. Tauri path stays working. Env docs match code.

### Phase D — Cleanup (Task 13)
Deliverable: dead code removed, repo lighter.

## What an agentic engineer should do

1. Read `02-DECISIONS.md` first — it explains *why* each choice was made. If you disagree with a decision, raise it before implementing; do not silently diverge.
2. Read `03-TASKS.md` for the ordered task list.
3. For each task, read `tasks/NN-name.md`, then implement. Tasks reference templates in `templates/` that you can copy as a starting point.
4. After each task, run the verification step listed at the bottom of the task doc.
5. After all tasks, run `verification/acceptance-checklist.md` end-to-end.

- Phase C: 4–6 hours
- Phase D: 30 minutes

Total: ~1.5 days. Most of the time is in Phase B/C testing on a clean environment.

## Risk

- **Snapshot DB drift**: the embedded `seeds/seed-snapshot.db` may go stale as the Prisma schema evolves. Mitigation: re-run `bun run seed:snapshot` as part of the release process; document in `runbooks/release.md`.
- **`setup-router.ts` API drift**: the Next.js proxy routes depend on the request/response shape `setup-router.ts` expects. Mitigation: the task spec includes a contract test that asserts the shapes match.
- **Tauri path divergence**: this pack fixes the NSIS path; the Tauri-CLI path (port 9421, Rust supervisor) is already mostly working. Don't break it.
