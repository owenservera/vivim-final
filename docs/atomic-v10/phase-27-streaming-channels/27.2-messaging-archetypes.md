# Unit 27.2: Messaging Provider Archetypes

**Phase:** 27 | **Files:** `src/engines/provider-mux.ts` (extend), `src/engines/streaming-channel-caps.ts`
**Depends:** 27.1 | **Class:** CREATE

## Purpose
Define provider archetypes for the common messaging surfaces so `channel_add` knows
how to connect, poll, and normalize messages for each. Mirrors how `seeds/providers/*.json`
already define AI provider manifests; messaging providers get the same shape with a
`kind: 'messaging'` discriminator.

## Interface
```ts
export interface MessagingArchetype {
  providerId: string            // 'whatsapp' | 'facebook' | 'telegram' | 'slack' | 'dispatch'
  loginUrl: string
  pollStrategy: 'webhook' | 'polling' | 'cdp-scrape'
  normalize(msg: unknown): NormalizedMessage
}
```
`NormalizedMessage = { channelId, author, text, ts, threadId? }`.

## Implementation
- New `archetypes.ts` (or inline in `streaming-channel-caps.ts`) exporting a registry
  `MESSAGING_ARCHETYPES: Record<string, MessagingArchetype>` for the five providers.
- `channel_add` looks up the archetype by `providerId`; if unknown → error
  ("unsupported channel").
- Each archetype's `pollStrategy` decides how `ProviderMuxEngine` ingests it (27.6):
  `webhook`/`polling` for API-based (Telegram/Slack), `cdp-scrape` for surfaces that
  need a logged-in browser (WhatsApp Web / Facebook).
- `normalize` maps provider-specific payloads to `NormalizedMessage` so downstream
  conversation ingestion is uniform.

## Tests
- `MESSAGING_ARCHETYPES.whatsapp.pollStrategy === 'cdp-scrape'`.
- `normalize` on a raw WhatsApp payload yields a `NormalizedMessage` with `channelId`.
