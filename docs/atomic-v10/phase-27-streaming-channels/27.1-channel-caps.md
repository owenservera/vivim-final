# Unit 27.1: Streaming Channel Capability Catalog

**Phase:** 27 | **Files:** `src/engines/streaming-channel-caps.ts` (new)
**Depends:** 24.1, 24.3 | **Class:** CREATE

## Purpose
Let the system ingest external messaging feeds (WhatsApp, Facebook, Telegram, Slack…)
as **streaming channels** addressable by NL (Scenario 1b: *"add new streaming channels
like my facebook messaging feed, my whatsapp"*). Each channel op is a `UnifiedCapability`
so CLI, UI, and `/api/interpret` register/connect/list identically.

## Interface
```ts
// src/engines/streaming-channel-caps.ts
export function registerStreamingChannelCaps(
  registry: UnifiedCapabilityRegistry,
  deps: { store: ChannelStore; mux: ProviderMuxEngine },
): void

//  cap:channel:add       { providerId, name? }      // register a channel source
//  cap:channel:remove    { channelId }              // destructive
//  cap:channel:list      { }
//  cap:channel:connect   { channelId, auth? }       // run login wizard (27.5)
```
`surfaces: ['cli','ui','api','mcp']`; `remove` → `requiresConfirmation: true`.

## Implementation
- New `src/engines/streaming-channel-caps.ts`. `registerStreamingChannelCaps` registers
  the four capabilities.
  - `add`: creates a `ChannelRow` (new `ChannelStore` contract in `storage/contracts/`)
    keyed by `providerId`; returns `channelId`.
  - `connect`: delegates to the auth flow (27.5) — launches the provider's login surface
    via the governor, captures session, marks channel `connected`.
  - `list`/`remove`: CRUD over the `ChannelStore`.
- The actual message ingestion is wired in 27.6 (mux subscribe).
- Add `ChannelStore` contract + `channel-store-impl.ts` (mirror the existing
  `storage/impl/*-store-impl.ts` pattern) for persistence.

## Tests
- `channel_add {providerId:'whatsapp'}` returns a `channelId`; `channel_list` includes it.
- `channel_remove {channelId}` requires confirmation; after confirm, `channel_list` no longer includes it.
