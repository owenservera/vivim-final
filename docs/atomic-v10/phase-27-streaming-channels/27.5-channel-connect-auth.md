# Unit 27.5: Channel Connect Auth Flow as Capability

**Phase:** 27 | **Files:** `src/server/setup-router.ts` (reuse), `src/engines/streaming-channel-caps.ts`
**Depends:** 27.1, 27.3 | **Class:** PORT

## Purpose
`channel_connect` must perform a real login for the messaging provider (QR / OAuth).
The system already has a provider setup + login-verification flow
(`/api/setup/launch-visible`, `/api/setup/verify`, `setup.complete` in
`capability-bootstrap.ts`). Port that flow into the `channel_connect` capability so
connecting a channel is the same capability path from CLI and UI.

## Interface
```ts
// cap:channel:connect handler orchestrates:
//  1. fleet_start { providerId }            (spawn slave on loginUrl from seed)
//  2. setup.launch-visible / QR capture
//  3. setup.verify (poll until logged in)
//  4. mark channel connected in ChannelStore
```
Returns `{ channelId, status: 'connected' | 'awaiting_login' }`.

## Implementation
- `channel_connect` handler (27.1) closes over `governor` + `ChannelStore`.
- Reuse `fleet_start` (`cap:fleet:start`) to spawn the slave on the archetype's
  `loginUrl`; reuse `setup.verify` to detect login state.
- If auth needs a human (QR scan), return `status: 'awaiting_login'` + a
  `clarification`/`requiresConfirmation` style prompt (25.6) so the UI can show the QR.
- On success, persist `connected: true` and emit `channel:connected` on the eventBus.

## Tests
- `channel_connect {channelId}` with a mocked governor+verify returns `status:'connected'`.
- When verify reports not-logged-in, returns `status:'awaiting_login'` (no crash).

## Gate
- typecheck + unit test with mocked governor.
