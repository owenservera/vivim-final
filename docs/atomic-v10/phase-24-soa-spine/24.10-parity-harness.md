# Unit 24.10: Parity Test Harness Skeleton

**Phase:** 24 | **Files:** `tests/e2e/cli-frontend-parity/run.ts` (new)
**Depends:** 24.1, 24.2, 24.3, 24.8, 24.9 | **Class:** CREATE

## Purpose
Provide the scaffolding that Phase 30 fills in. A reusable harness that, for every
capability registered with `surfaces: ['cli','ui']`, exercises it **twice** — once
via the CLI argv path and once via the HTTP path — and asserts the two structured
outputs are equivalent. This is the mechanism that enforces the "CLI = Frontend"
invariant and makes it testable from day one, before any capability exists.

## Interface
```ts
interface ParityCase {
  capabilityId: string
  cliArgs: string[]            // e.g. ['providers','list']
  httpBody: { input: Record<string, unknown>; ctx?: unknown }
  normalize?: (out: unknown) => unknown  // strip volatile fields (latency, traceId)
}
interface ParityResult {
  capabilityId: string
  cli: unknown
  http: unknown
  equal: boolean
  diff?: string
}
```

## Implementation
- New `tests/e2e/cli-frontend-parity/run.ts` exporting `runParity(cases: ParityCase[])`:
  - Spawns a booted server on `127.0.0.1:9420` (reuse devops test bootstrap).
  - CLI path: `bun run src/cli/index.ts <cliArgs> --remote http://127.0.0.1:9420 --json`.
  - HTTP path: `fetch('http://127.0.0.1:9420/api/capabilities/<id>/execute', POST)`.
  - Normalize both (drop `latencyMs`, `traceId`, `ok`), deep-equal via `structuredClone` diff.
- `tests/e2e/cli-frontend-parity/index.test.ts` — empty `cases: []` for now; the
  registry introspection (`GET /api/capabilities?surface=cli`) discovers eligible
  cases automatically once Phase 24.4-24.6 populate the registry.
- Keep the harness surface-agnostic: it only knows `surface: cli` vs `surface: ui`;
  the equivalence check is on the resolved `output`, never on presentation.
