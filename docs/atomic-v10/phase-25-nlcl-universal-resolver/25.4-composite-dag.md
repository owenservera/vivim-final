# Unit 25.4: Composite / Pipeline DAG via Registry

**Phase:** 25 | **Files:** `src/engines/nlcl/nlcl-engine.ts`
**Depends:** 25.1 | **Class:** EXTEND

## Purpose
`NLCLEngine` already detects composites ("go to cnn and summarize the news") and
runs `executePipeline`/`routeComposite` (`nlcl-engine.ts:235`). But the steps are
resolved as raw `ParsedIntent`s that hit the executor router directly. Wire composites
to the **registry**: each step resolves to a `capabilityId`, and execution goes
through `registry.execute(id, input, ctx)` — the same universal transport used by the
CLI and frontend (Invariant #2: one transport).

## Interface
```ts
// internal: each composite step becomes
{ capabilityId: string, input: Record<string, unknown>, ctx: CapabilityContext }
```

## Implementation
- In `executePipeline`/`routeComposite`, replace direct `router.route(step)` calls
  with `this.deps.registry.execute(step.capabilityId, step.input, toCapCtx(ctx))`.
- `toCapCtx` maps `NLCContext` → `CapabilityContext` (the registry's context shape:
  `conversationId`, `providerId`, `slaveId`, `userId`, `metadata`).
- Pipeline chaining (`pipelineData` threaded into the next step's `content` input)
  stays as-is — it is the data-flow primitive; only the execution sink changes.
- Guard: if a step has no `capabilityId` (legacy pattern), fall back to
  `router.route` so old patterns still work during the transition.
- `classification` of the composite result = max of step classifications
  (reuse `classificationAtLeast` from `types.ts`).

## Tests
- `interpret('go to cnn and summarize the news')` executes `browser_navigate` then
  `content_summarize` via `registry.execute` (assert `registry.execute` spy called twice).
- Registry missing a step's capability → that step surfaces as failed with a clear error.
- Pipeline propagation: summarize step receives the navigate step's output as `content`.

## Gate
- typecheck + unit test asserting registry.execute is the execution path.
