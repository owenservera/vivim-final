# Unit 25.3: LLM-Slave Resolver

**Phase:** 25 | **Files:** `src/engines/nlcl/llm-slave-resolver.ts` (new), `src/engines/nlcl/intent-resolver.ts`
**Depends:** 25.1, 25.2 | **Class:** CREATE

## Purpose
The deterministic catalog covers ~95% of commands, but novel sentences like
*"change my canvas background to an image of the moon made out of cheese"* have no
pattern. The LLM-slave resolver reuses the **provider LLM the user is already
talking to** (the Chrome slave's logged-in session) to parse the sentence into a
target capability + typed input, grounding against the live catalog. This is the
"NLP formats to system-level commands" heart of the requirement.

## Interface
```ts
export interface LLMSlaveResolverDeps {
  providerLLM: ProviderLLMAdapter     // talks to the logged-in slave's provider
  catalog: () => CommandPattern[]     // current capability/pattern catalog
}

export class LLMSlaveResolver implements IntentResolver {
  readonly name = 'llm-slave'
  resolve(rawInput: string, ctx: NLCContext): Promise<ParsedIntent | null>
}
```
The resolver issues a constrained prompt: "Given this catalog of capabilities
(id, description, inputSchema), map the user sentence to ONE capabilityId + JSON
input. Reply ONLY with JSON `{capabilityId, input}`." It validates the model's JSON
against the target capability's `inputSchema` (`ZodSchema` from `catalog.ts`).

## Implementation
- New `llm-slave-resolver.ts`. `ProviderLLMResolver` already exists in
  `intent-resolver.ts`; this unit adds the catalog-grounded variant that (a) injects
  the catalog into the prompt, (b) parses + validates the JSON, (c) returns a
  `ParsedIntent` whose `intent` === `capabilityId`.
- `NLCLEngine` selects this resolver when `ctx.providerId` resolves to a running
  slave (governor has an instance) **and** the deterministic/layered resolver fell
  below `minConfidence`. Reuse `tryAIFallback` path so the existing
  `enableAIFallback` flag gates it.
- Validation failure (bad JSON / schema mismatch) → return `null` → flows to
  clarification (25.6) instead of silently failing.
- Cap token spend: only invoked for the unresolved tail; never for composite halves
  already resolved deterministically.

## Tests
- With a mocked `ProviderLLMAdapter` returning `{"capabilityId":"cap:canvas:set_background","input":{"imageQuery":"moon made of cheese"}}`,
  `resolve("...moon made of cheese...")` returns that intent with `confidence: 1`.
- Malformed model JSON → `null`.
- Schema-invalid input from model → `null` (drives clarification, not a crash).

## Gate
- typecheck + unit test with mocked adapter (no live Chrome required).
