# Unit 28.1: Workflow-as-Capability

**Phase:** 28 | **Files:** `src/engines/workflow-engine.ts` (extend)
**Depends:** 24.1, 24.3 | **Class:** PORT

## Purpose
A compiled `WorkflowDefinition` (already modeled in `WorkflowEngine`) should be
invocable like any other capability — `POST /api/capabilities/:id/execute`. This makes
workflows first-class citizens of the unified registry (Invariant #1) and exposes them
to CLI, UI, and `/api/interpret` on equal footing with built-ins.

## Interface
```ts
// WorkflowEngine gains:
async registerAsCapability(
  workflow: WorkflowDefinition,
  registry: UnifiedCapabilityRegistry,
): Promise<void>
// → registry.register({
//     id: `cap:workflow:${workflow.id}`, slug: `wf_${workflow.name}`,
//     surfaces: ['cli','ui','api','mcp','workflow'],
//     inputSchema: <derived from workflow.variables>,
//     handler: (input) => this.executeWorkflow(workflow.id, input),
//   })
```

## Implementation
- Extend `WorkflowEngine` with `registerAsCapability`. Derive `inputSchema` from the
  workflow's `variables` (each var → a property; required if no default).
- Handler calls the existing `executeWorkflow` (the engine already runs node DAGs with
  HITL). Mark `workflowNodeType: 'workflow-root'` so it can be nested in other workflows.
- `workflow_create` (28.2) registers the compiled workflow as a capability immediately.
- `unregister` path: deleting a workflow also `registry.unregister`s its capability.

## Tests
- After `registerAsCapability`, `registry.get('cap:workflow:demo')` exists and its
  handler runs the workflow end-to-end.
- `GET /api/capabilities?surface=cli` includes the workflow capability.
