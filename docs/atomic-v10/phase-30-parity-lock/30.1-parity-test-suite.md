# Unit 30.1: CLI ↔ Frontend Parity Test Suite

**Phase:** 30 | **Files:** `tests/e2e/cli-frontend-parity/index.test.ts` (extend from 24.10)
**Depends:** 24.10, 25.8, 25.9, 29.2, 29.3 | **Class:** CREATE

## Purpose
Lock Invariant #4 (Symmetric surfaces): every capability marked
`surfaces: ['cli','ui']` MUST be reachable and produce identical structured output
from both the CLI argv path and the HTTP/UI path. This is the enforcement gate of v10.

## Interface
```ts
// auto-discovered cases:
const caps = await GET('/api/capabilities?surface=cli')   // also ui
for (const cap of caps.filter(c => c.surfaces.includes('ui'))) {
  assertParity(cap.id, cliArgsFor(cap), httpBodyFor(cap))
}
```
`assertParity` runs the 24.10 harness and fails the suite on any mismatch.

## Implementation
- Extend `tests/e2e/cli-frontend-parity/index.test.ts` to discover eligible capabilities
  from the running server and assert parity for each.
- `cliArgsFor` derives argv from `cap.cliCommand.name`; `httpBodyFor` derives the
  `POST /api/capabilities/:id/execute` body from `cap.inputSchema` (seeded with the
  same fixture inputs used for the CLI).
- Volatile fields (`latencyMs`, `traceId`, `ok`) normalized away before compare.
- Covers each scenario in SOA-ARCHITECTURE §4 (canvas, channels, workflow, session)
  once those phases land.

## Tests
- The suite fails if any `surfaces:['cli','ui']` capability is unreachable from either path.
- A deliberately divergent output (test double) fails the suite (guards the assertion).

## Gate
- `bun test tests/e2e/cli-frontend-parity` green across all registered dual-surface caps.
